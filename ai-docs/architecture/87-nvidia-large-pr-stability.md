## Почему большие PR теряются

1. Всё или ничего. Runtime отдаёт весь PR одному процессу OCR, OCR сам делит файлы на группы до 10 файлов и проходит их по одной. Внутри OCR сбой группы локален, но после любого неподтверждённого сбоя запроса срабатывают четыре забора:
   - транспорт runtime (`inferenceDenied`);
   - журнал диспетчеризации runtime (`failed()` после отправки ставит `fenced`);
   - допуск заявки в RR (`model_dispatch_effect_unresolved`: пока у прогона есть заявка в `dispatch_may_have_started` или `effect_unknown`, новая не выдаётся);
   - приёмка наблюдения в RR (`review-model-dispatch-evidence.ts`: каждая заявка слота, кроме `not_dispatched`, должна быть `completed`).

   Затем приёмка runtime выбрасывает весь результат (`gateway_effect_unknown`). Исключение есть только для подтверждённого лимита вывода (#401): такой запрос закрывается как `completed`.
2. Потолок 128 запросов на прогон (`model-dispatch-policy.capacity128.v1`). После Action 242 вытесненные пушем прогоны #665 успевали сделать 74-121 запрос за 55-67 минут. Когда остальные потери уйдут, следующей стеной для огромных PR станет потолок, а его исчерпание сейчас тоже выбрасывает всё сделанное.
3. Время. 21-60 файлов занимают 45-80 минут. Авторы пушат или сливают раньше: 65 исполнений вытеснены или PR слит, это 1230 минут работы OCR против 1034 минут у всех потерь вместе. Параллелить нельзя без смены того же правила допуска RR: оно держит один запрос в полёте на прогон.
4. Каждый запрос модели 4 раза перечитывает ревизию PR в GitHub (relay `full` check до отправки, после ответа, до и после статуса). Сбой любой проверки в конце длинного ревью выбрасывает всё.

NVIDIA как провайдер редко отказывает: за окно 5 x 429 и всплеск не-2xx утром 18.11 на 4515 запросов. Но её скорость (30-40 с на запрос) вместе с нашей строго последовательной схемой и есть причина самого большого класса (вытеснение). Убежавшие ответы (0,7%) - её второе слабое место.

## Шаг 1: известная остановка сохраняет сделанное (runtime, DO)

Правило "неизвестный эффект закрывает прогон" не меняется. Почему остановка по потолку безопасна:

- Отказ в заявке (локальная граница или ответ RR 409 `model_dispatch_budget_exhausted` внутри транзакции) доказывает, что этот запрос не выходил из раннера.
- До проверки потолка доходит только журнал диспетчеризации runtime без забора. Любой прошлый запрос с неподтверждённым или неизвестным исходом ставит забор (`failed()` после отправки, неподтверждённая квитанция), и журнал отказывает раньше потолка. Значит, все прошлые заявки закрыты как `completed` с native-доказательством или как `not_dispatched`, и приёмка наблюдения в RR (`review-model-dispatch-evidence.ts`) пройдёт.
- Ответ RR 409 по потолку сам по себе этого не доказывает: RR проверяет потолок раньше неопределённости. Инвариант держит журнал runtime, и шаг 2 должен его сохранить.

1. Транспорт записывает такой отказ как `{code: model_dispatch_budget_exhausted, effect: not_dispatched}` вместо `effect_unknown`. Вывод остаётся закрытым, журнал диспетчеризации остаётся с забором.
2. Одна семантика для двух известных остановок (потолок и лимит вывода): атрибуция модели остаётся, пока записанный факт - известная остановка. Остановка отмечается по месту наблюдения, а не по коду: тело ответа relay или Gateway с `output_truncated` или `model_dispatch_budget_exhausted` становится `relay_unknown`/`effect_unknown`. Более неопределённый поздний сбой заменяет остановку, отмена снимает атрибуцию. Поэтому и 4-й лимит вывода (забор #401) больше не выбрасывает сделанное (пометка к плану 85).
3. Приёмка OCR принимает оба факта как известную остановку: результат всегда частичный (`context_inspection_incomplete` + `provider_warning`). Любой другой `not_dispatched` по-прежнему `review_agent_not_dispatched`, любой другой оплаченный или неизвестный эффект по-прежнему отказ.
4. Честный счёт файлов: адаптер OCR запоминает пути групп, у которых не завершился основной проход (`mainCompleted: false`), и пути без группы. Проекция того же прогона помечает их `unreviewed` ("the review stopped before this file was finished") и не считает проверенными. Это касается любого частичного OCR-ревью с незавершёнными группами, в одиночном пути и в дорожках ростера. Исключение: прогон, восстановленный в новом процессе после приёмки (путь restore-only), этих данных не имеет и считает файлы слота как раньше.
5. Прогресс-комментарий RR (`github-progress-comment.ts`) при неполном итоге больше не печатает "Files fully reviewed: N of N": он считает файлы по принятым частям и не знает, какие из них остановились рано. Точный счёт остаётся в сводке. Контракт не меняется.
6. Сводка: закрытое уведомление "the review used its whole allowance of model requests before it reached every file". Ключей в контракте с RR нет.
7. Прогон остаётся красным, как любое неполное ревью.
8. Тесты только на рискованное: TLS-проба транспорта (2 запроса закрыты, третий отказан, атрибуция сохранена, дальше отказ локально, квитанции `completed, completed`, отмена снимает атрибуцию; тело 502 с `output_truncated` не открывает атрибуцию; 4-й лимит вывода ставит забор и оставляет атрибуцию), приёмка (частичный результат; тот же код с другим эффектом и другие `not_dispatched` по-прежнему отказ), флаги и незавершённые пути адаптера, счёт файлов в проекции, строка прогресса, текст уведомления.

Прямое доказательство, что OCR отдаёт результат на потолке: прогон 44107903572 (#821) после 128 запросов вышел из OCR с кодом 0, runtime отказал только на приёмке.

## Шаг 2: сбой одного запроса роняет только его группу (рекомендую, решение владельца)

Обобщение #401 на неизвестный эффект. Оно меняет правило "неизвестный эффект закрывает прогон" в RR и в runtime, поэтому нужно согласие владельца.

1. RR, допуск заявки (`prisma-review-run-companion-dispatch-repository.ts`): отказывать, пока есть заявка в `dispatch_may_have_started` (один запрос в полёте остаётся инвариантом) или когда `effect_unknown` у прогона уже 3.
2. RR, приёмка наблюдения (`review-model-dispatch-evidence.ts`): разрешить до 3 заявок слота в `effect_unknown`, если приёмка runtime пометила результат частичным.
3. Runtime, журнал: `failed()` такого запроса не ставит вечный забор, следующий резерв ждёт закрытия квитанции прошлого. Вспомогательные транспорты (описание PR, проверка жизненного цикла) делят этот журнал: правило для них решается явно.
4. Runtime, транспорт: allow-list причин с сохранённой причиной до `fail()`:
   - обрыв потока после 200 без отмены вызывающим и без нарушения целостности (`terminal_evidence_invalid`, `settlement_unconfirmed`, превышение байт);
   - финальный 400 или 5xx без `failureScope`, квоты и кодов насыщения, решение по уже прочитанному телу отказа.

   Все записи факта идут через `recordFailure`. Точный повтор тела запрещён по хешу. Бюджет общий с #401: 3 запроса на потребителя, дальше известная остановка как в шаге 1.
5. Один владелец политики: транспорт отдаёт факты для приёмки вместо 4 копий `effectFacts` (`account-gateway-runtime.ts`, `account-gateway-reviewer-session.ts`, `provider-api-runtime.ts`, `prepared-model-review-runtime.ts`). Явно решить, входят ли путь provider API и ростер (у ростера журнала нет).
6. Выкатка парная: сначала RR API (старый Action после неизвестного эффекта заявок не делает), потом Action. Новый Action со старым RR деградирует безопасно: заявку отклонят, ревью потеряется как сейчас.

Что ещё нужно решить до реализации шага 2:

- Откуда RR узнаёт "частичный": у проверки evidence нет входа с флагами наблюдения.
- Одна единица счёта неизвестных: допуск считает на прогон, приёмка на слот. Прогон лучше: на него приходятся и проверка жизненного цикла, и описание PR.
- Одно число в двух местах (3 в runtime и в RR): один владелец, например поле лимита в capability диспетчеризации.
- Порядок проверок: RR проверяет потолок раньше неопределённости, сочетание "отказ по потолку при до 3 `effect_unknown`" нужно описать и проверить тестом между репозиториями. Инвариант шага 1 (журнал без забора) при этом исчезает и должен быть заменён явным правилом.
- Не проверено, примет ли Gateway следующий запрос того же исполнения после 502 или неизвестного эффекта без `recoverSameOperation`. Без этого оценка в 2 дня ненадёжна.
- 400 от relay приходит только с `not_dispatched` и не должен тратить лимит неизвестных.

Цена: до 3 возможно оплаченных запросов на прогон, их вывод не используется.

## Риски шага 1

- Огромные PR будут работать до потолка (65-85 минут при 30-40 с на запрос; #821 дошёл за 80 минут) и публиковать частичное ревью. Раньше они так же долго работали и не публиковали ничего, но теперь чаще доживут до потолка и дольше держат раннер, а раннеров и так не хватает.
- Если потолок или лимит вывода поймает шаг OCR уровня прогона (группировку), процесс выйдет не 0, и ревью потеряется как раньше. До #401 в 7 прогонах #665 первый запрос (вероятно, группировка) упирался в лимит вывода; после #401 OCR в этом случае делит файлы по одному.
- Частичное ревью остаётся красным. Сделать его нейтральным - решение владельца.
- Вытеснение пушем (30 из 71 исполнения после Action 242) шаг 1 не лечит.

## 2. Проверено, дефекта нет

- Цепочка fallback (#892): у каждого запроса свой `callId` (`requestRef` = хэш ревьюера + UUID, relay:1485-1487), у ревьюеров свои allocation. Отказ до отправки не входит в requests и токены, но модель видна в run и Models. Запрос, ушедший к провайдеру, - один request. Двойного счёта нет. Сценарий (отказ, квота, принятый запасной, rerun) проверен в памяти и тем же набором на PostgreSQL 17 через `PrismaUsageReportReader` (`usage-reviewer-chains.test.ts`, `prisma-usage-store.test.ts`).
- До native-сверки вызов с исходом `effect_unknown` - «без отчёта usage», не request; после сверки KPI requests растёт задним числом. Это честно: lifecycle не доказывает, что провайдер обработал запрос.
- Пропуск по квоте (#888): новых вызовов у пропущенного ревьюера нет, сам отказ записан как обычный вызов с исходом. Statistics считает такое ревью один раз (`completed`).
- Один прогон на ревизию (#891) на Usage не влияет: run = GitHub run ID; rerun (`runAttempt` 2, новая authorization) сливается в ту же строку Runs.
- SQL-отчёт совпадает с эталоном в памяти (PG17-паритет). Порядок устаревших `groups` (только operator-страница) идёт по первому `callId`, а не по порядку входа эталона.
- Суммы: requests и токены строк Models и Daily складываются в KPI; `logicalRuns` неаддитивен и в Models не показывается. Дни Usage - из UTC-строки `occurredAt`; Statistics хранит `TIMESTAMP(3)` без зоны, прошлый период той же длины (`statistics-policy.ts:46-59`).
- Statistics не считает partial-ревью - решение плана `2026-10-23-review-statistics.md:31-36`.
- NVIDIA: профиль `nvidia-build-chat-apikey-v1` с источником `nvidia` есть уже в первом NVIDIA SDK (`c32ef9ed3360`, 2026-11-11), поэтому строки NVIDIA по коду не бывают `unknown`. На prod не проверено (см. 4.6).
- Известные ограничения, не баги: (а) «30 дней» в Usage - скользящие 720 часов, в Statistics - календарные дни UTC, суммы двух страниц могут расходиться; (б) summary-семья direct-маршрута на границе окна: summary берётся целиком, а дети вне окна попадут в соседний период (`prisma-usage-report.ts:143-183`), сумма двух периодов больше их объединения. Gateway v4 это не касается: turn-факт runner не пройдёт проверку durable identity.

## 3. Дефекты и исправления (этот PR, только Web)

2. «Runtime delivery: unknown (no producer coverage report)» - строка на каждый grant за период (`provider-usage-details.tsx:73-82`), почти на каждый прогон. Producer шлёт отчёт только о потере (`domain/usage.ts:342-353`). Теперь строки только для потерь плюс одна «No delivery loss reported by N runtime sessions».
3. Фильтры Binding/Run из Details фильтруют всю страницу, но «Reset filters» их не учитывал (`provider-usage-view.tsx:356-371,657-673`). Теперь учитывает и сбрасывает.
4. Опрос каждые 30 с шёл и при `unknownCostCount`/`unknownTotalTokenCount` (`provider-usage-view.tsx:41-48,125-128`, добавлено в #673). У Gateway цены нет никогда, значит страница бесконечно перечитывала тяжёлый отчёт и кнопка мигала «Refreshing…». План 61:200-201 разрешает опрос только при unknown/partial; теперь так. Подпись в Details по-прежнему учитывает цену.
5. Остатки «Unknown» для того, что источник не прислал: `count`/`compact` (`provider-usage-format.ts:4-14`, отсюда KPI «Known tokens»), подпись цены (`:39,44`, подсказка Cost писала «Unknown · some cost not reported»), в Details - unattributed у участника (видно только админу), lag и окна без native-источника, direct coverage без direct-вызовов. ## 4. Открытые решения (нужен выбор владельца)

1. Коррекция при чтении правит только строки `codex`. Вендора профиля знает только Web (`subscription-profiles.ts`, `provider-identity.ts`). Риски смены метки: проверка `accept` сравнивает identity с пересчитанной меткой (`provider-usage-routes.ts:642,694-713`, v3 - метка grant `:401`), окно - весь replay grant до ~8 дней (`:355-357`), отказ теряет весь batch вместе с `producerCoverage`; словари разные (Usage `codex`, Web `openai`/`anthropic`) - смена режет facets, фильтры и историю; diagnostic-строки join не исправит (нет authorization).

2. «Included in subscription». Профиль (OAuth Codex/Claude/Grok, coding plans) восстановим из замороженного снимка тем же join. Вопрос семантики: подписка всё равно тратит лимиты, NVIDIA trial - кредиты.

   - Оценка «API-эквивалента» по публичным ценам. Надёжность 5/10, уверенность 6/10 (легко принять за счёт).
3. Completeness Gateway: «partial» приходит и без счётчиков (#882). Нужен `unknown` в контракте Gateway (репозиторий `agent-teams-ai/account-gateway`, `services/account-gateway/src/usage.ts`). В RR менять нельзя: смена маппинга меняет хэш фактов (`prisma-usage-store.ts:137-140`).

План 61 задал возрастание, поэтому не меняю без решения; затронет SQL, эталон и E2E.
6. На prod #882 видел 79 вызовов без отчёта usage. Без prod не понять, зависшие ли это `prepared`/`effect_unknown` или несопоставленные native-наблюдения (`Unattributed observations`). Нужен read-only запрос по `UsageCall` за 30 дней (и заодно провайдеры строк NVIDIA).

## 6. Решения 1-3: реализация (v3, вторая поставка)

- Один владелец identity профиля - Gateway SDK ([agent-teams-ai/account-gateway#113](https://github.com/agent-teams-ai/account-gateway/pull/113)): `providerConnectionIdentity(profileId)` и список `providerConnectionIdentities` (вендор и план 9 квалифицированных профилей). Реестр сервиса берёт их оттуда, вывод `provider-connections/v1` прежний.
- RR: `packages/features/provider-usage/src/infrastructure/gateway-profile-provider.ts` переводит вендора SDK в словарь Usage (`openai` → `codex`, `anthropic` → `claude`, остальные как есть). Его используют `providerUsageConfiguredProvider` (новые строки: `glm`, `minimax`, `kimi`, `grok`, `claude`, `mimo`) и коррекция при чтении: строки `codex` и `unknown` с профилем из замороженного снимка получают вендора, исходные факты не меняются. В v4 `accept` сравнивает провайдера с серверной durable identity, поэтому отчёты вызовов, подготовленных до смены меток, проходят. Для v3 runner-отчёты прогонов, идущих во время выката, могут получить `usage_scope_mismatch`; native-usage этих вызовов не затронут.
- Completeness: Gateway шлёт `unknown`, когда счётчиков нет вообще; RR принимает `unknown`, `partial` и `complete`, сохранённые `partial` остаются. Статус строки теперь «N calls without token counts» (нет отчёта или нет счётчиков).
- «Included in subscription»: отчёт несёт `subscriptionProviders` (провайдеры Usage, у которых все профили Gateway - подписка, coding plan или M plan; один pay-as-you-go профиль вендора снимает метку). Метка ставится, только если все вызовы строки идут через Gateway и цены нет ни в какой валюте; direct-ключ может быть оплатой за токены, поэтому без метки. NVIDIA trial, OpenRouter и MiMo (план `unknown`) метку не получают.
- Порядок выката: RR с новым SDK, затем Gateway с #113 и [#114](https://github.com/agent-teams-ai/account-gateway/pull/114) (повтор той же ревизии со старым `partial` без счётчиков равен `unknown`, без конфликта). Старый SDK отвергает страницу с `unknown`, и сверка Usage стоит (без потерь), пока RR не догонит. После выката Gateway откат только вперёд: старый код не читает сохранённые `unknown`. Смена SDK меняет conversation source stamp - нужна повторная квалификация conversations.
- Остаток: Web по-прежнему называет вендора профиля сам (`provider-identity.ts`, `subscription-profiles.ts`, env `REVIEW_ROUTER_ACCOUNT_GATEWAY_MIMO_PROFILE_ID`). Gateway принимает в конфигурации только профили своего реестра, а единственный профиль MiMo там - `openai-responses-apikey-v1`, поэтому метки совпадают. Перевести Web на `providerConnectionIdentity` - отдельный шаг.

Статус: реализовано. B - PR #910 (мёртвые экспорты и общий маппинг), A - PR с этим изменением статуса (потолок `max-lines` для apps/web: 600 для новых файлов и замороженные потолки 28 существующих гигантов, сняты с main `061f04bc2` после всех UI-волн 76-82). C - DROP, D и E - DEFER. План v4 (R7, раунды ревью 1-3), дата плана 2026-11-18, база плана: main `ae18f9e87`, PR #901 и черновики 77-82.

## 1. Факты

- В `eslint.config.mjs` нет `max-lines`, `max-lines-per-function`, `complexity`. `pnpm lint` (шаг Lint в Static Checks, `ci.yml:557`) идёт 24 s, 0 предупреждений.
- Код apps/web без тестов и vendor: 28 файлов длиннее 600 строк, из них 11 длиннее 1000 (замер ESLint `max-lines` на Hetzner). По всему репозиторию 231, остальное - api, packages и разовые rollout-скрипты вне accounts/providers.
- Рост: `account-gateway-account-controls.tsx` 1247 (2026-10-15) → 2832 (10-29) → 2987, на head #901 3026; `personal-account-controls.tsx` 1790, на head #901 1889. Функции-гиганты: `ProviderChoiceStep` 1454 строки, `createAccountsAdapter` 1285, `Controls` 924, `PersonalControls` 718.
- Копипасты мало: jscpd по accounts/providers - 0.29% строк. Проблема в размере и в том, что 4-5 тем партии правят одни и те же файлы.

## 3. Пользователь и кому хуже

Экран не меняется, это гигиена разработки, поэтому A - решение владельца. Связь «большой файл → регрессии» прямо не доказана. Доказано другое: каждая фича октября дописывала в один компонент (+1585 строк за 2 недели), и сейчас 4 UX-темы правят его одновременно. Минимальный A стоит около 45 строк конфига и не даёт следующей UX-фиче снова дописать в 3000-строчный файл.

Кому хуже: автору PR, которому надо дописать в файл из списка. Он выносит затронутый блок по §6 или поднимает потолок в конфиге с причиной в описании PR (это видно в diff). Уменьшение файла ничего не требует.

## 4. Потолок (A): минимальный вариант

- Всё в `eslint.config.mjs`, без скриптов и отдельных файлов данных: один блок для `apps/web/**/*.{ts,tsx,mts,cts,js,mjs,cjs}` кроме тестов (`**/*.test.*`, `**/*.spec.*`, `**/tests/**`) и `apps/web/app/vendor/**` (сторонний код) с `max-lines: ["error", { max: 600 }]`; затем компактная карта `const maxLinesCeilings = { "<путь>": <строк>, ... }` из ~28 существующих гигантов, развёрнутая в объекты `{ files: [путь], rules: { "max-lines": ["error", { max }] } }` (отдельный блок на файл после prettier дал бы ~130 строк, карта ~45). Проверено на ESLint 10.3.0: поздний объект переопределяет `max` для своего файла, `ignores` внутри объекта с `files` действует только на него, потолок = длина проходит, +1 строка - ошибка. Владелец счёта строк и набора файлов один - ESLint.
- Список снимается один раз с main после партии прогоном базового блока (ESLint с `max-lines` в формате json), поэтому тесты и vendor в карту не попадут; команда записывается в описание PR A, а не в репозиторий.
- Пути в `files` - маски minimatch. В текущих путях спецсимволов нет; если появятся (`[id]`, `(group)`), их экранируют вручную обратным слэшем.
- Потолки понижаются правкой одной строки карты в PR, который разбивает файл. Запись для удалённого файла ничего не ломает и удаляется там же.
- Почему не bulk suppressions ESLint: они считают число нарушений на файл, а `max-lines` даёт одно нарушение при любой длине, так что файл рос бы без предела.
- Обход через `eslint-disable` отдельно не ловим: он виден в diff так же, как поднятие потолка. Сейчас в apps/web таких комментариев нет.
- CI, `package.json`, turbo не меняются: шаг Lint уже вызывает `pnpm lint`. Пилот oxlint (`lint-format-test-support.mts:101-107`) копирует `eslint.config.mjs` целиком, а `eslint.native-fallback.config.mjs` импортирует его, поэтому новых файлов в обвязке не нужно.
- Замер на копии main: per-file потолки не меняют время lint (23.5 s против 23.9 s), +1 строка в гиганте и новый файл в 601 строку дают ошибку.
- AGENTS.md: одна строка - файлы с потолком в `eslint.config.mjs` не растут без причины в описании PR, затронутый блок сначала выносится (шаблон в архитектурном документе 83).

## 6. Шаблон разбиения (для вынужденных выносов и для D)

- Клиент (`app/dashboard/*` → `src/features/<feature>/`): фичи с логикой раскладываются по слоям [37](37-frontend-clean-architecture.md); свернуть папки 37 разрешает только маленьким фичам, которые только показывают данные. Плоские `src/features/account-gateway` и `provider-setup` - существующее отклонение: новый код в них идёт по слоям, остальное не переносится попутно. Разделение: (1) решения и производные состояния (что можно сохранить, какой шаг, какой статус) - чистые функции без React; (2) состояние, эффекты, React Query, sessionStorage-nonce - один хук на поток (`useConnectOperation`, а не общий `useAccounts`); (3) разметка - компоненты по одному понятию, получают view model и колбэки; (4) тексты - существующие `*-copy.ts`.
- Сервер по [03](03-feature-first-monorepo-structure.md): мутации (use cases) уходят в `packages/features/<feature>/application` (образец - `reconcile-workspace-binding-fences` в `provider-accounts`), а `apps/web/src/server` оставляет сборку (composition root), адаптер Gateway и read model. Если перенос в пакет не оправдан пользой, это записанный разрыв DDD (как 77 §8), а не новый слой в `src/server`.
- Порядок в PR: сначала перенос без изменения поведения (отдельный коммит, тесты переезжают вместе), потом правка. Без re-export прослоек и barrel-файлов, импорты обновляются сразу (пользователей нет). Новых абстракций и портов не вводить.

# Компактный комментарий ReviewRouter и необязательный баннер

Дата: 2026-10-21, Europe/Kiev. Статус: реализовано; presentation E2E через GitHub выполнен.
Проверки и границы доставки: [E2E evidence](../spikes/compact-review-comments-e2e-20261021.md).
Пользователь выбрал вариант «Сразу к проблеме». Base64 проверен на серверном
рендерере GitHub и исключён из способа публикации.

## 1. Принятое решение

Первый этап: компактный Markdown, полностью полезный без изображений.
Второй, независимый этап: небольшой баннер через HTTPS, если нужен брендированный
верх комментария. Генерировать его детерминированным SVG-шаблоном, без ИИ,
браузера, нового object storage и записи картинки для каждого review.

Подробный результат проверки: [GitHub base64 image rendering](../spikes/github-base64-image-rendering-20261021.md).

## 2. Где менять

- Public Action: `src/output/reviewer-summary.ts` и существующие тесты summary.
  На проверенном main `9e494fb9b8809dc5c91c9f4159edcca13b89fbde` именно
  `renderReviewerSummaryMarkdown` добавляет большой брендовый заголовок,
  нулевые счётчики, Summary, Release Notes, Findings и отдельные diagnostics.
  `formatter-v2.ts` уже является фасадом. Старый соседний local checkout
  не использовать как источник актуального formatter implementation.
- SaaS/GitLab summary: существующие
  `packages/features/review-publishing/src/domain/review-publication-summary.ts`
  и `review-publication-markdown.ts`, их тесты и publisher adapters.
- Сохранить существующие adapters и границы двух репозиториев. Не создавать
  новый межрепозиторный пакет или plugin framework ради оформления.
  Согласовать наблюдаемое поведение обоих renderers одинаковыми сценариями.
- Перед реализацией сверить актуальные main и локальные изменения: рабочая
  копия SaaS уже содержит чужие незакоммиченные изменения summary/publishing.
  Их не перезаписывать и не включать в собственную доставку.

## 3. Точный контракт первого экрана

1. Одна строка состояния: например `🔴 **1 critical finding**`.
   При разных severity показывать только ненулевые категории.
   Убрать отдельные `# ReviewRouter`, `## Summary`, повторяющий количество
   heading, Release Notes из названий ошибок, большой footer Powered by.
2. Неполное ревью, отказ provider, непроверенное покрытие и требующие внимания
   старые threads обозначать видимым текстом сразу под состоянием. Сохранить
   действующую семантику incomplete, coverage, lifecycle и dismissed findings.
   Нулевое число новых находок при неполном ревью не означает All Clear.
3. При 1–3 текущих находках показывать severity, название, место и короткий
   текст каждой находки. Текст брать из первого обычного абзаца существующего
   `message`/`body`, не более 320 символов до границы слова; добавлять многоточие
   при сокращении. Если первый блок является кодом, таблицей или HTML,
   не пытаться сделать из него смысловое резюме; оставить название и подробности.
   Не запускать дополнительную модель и не выдумывать Impact/Suggested fix.
4. При 4+ текущих находках использовать компактный список: severity, название,
   место, раскрываемое описание. Сортировка: severity, затем стабильный ключ;
   не менять fingerprint и не терять замечания с одинаковым местом.
5. Evidence, reasoning, большие фрагменты кода, suggestions и attribution
   хранить в раскрываемых подробностях находки. Отдельную строку исправления
   показывать только при наличии подходящего структурированного значения;
   existing `suggestion` с кодом показывать как code fence в подробностях.
6. Scope, метрики, provider diagnostics, анализ и граф объединить в один
   `Review details`. Внутри использовать подзаголовки, без дополнительных
   вложенных `<details>`. Не показывать отсутствующие или придуманные метрики.
7. Активные старые замечания учитывать по существующим lifecycle-правилам.
   Их количество и требуемое действие остаются видимыми; разрешённые прошлые
   threads и техническую историю можно перенести в Review details.
8. Все служебные надписи локализовать существующим механизмом. Оставить
   поддержанные языки и протокольные severity/fingerprint без переименования.

Ссылка на место в GitHub должна вести к указанному в результате head SHA и
правильной стороне diff/исходнику, с URL-encoding пути. Не привязывать результат
к текущему mutable main. При отсутствии безопасной ссылки оставить место кодом.
GitLab строит ссылки своим существующим adapter; ссылки GitHub туда не переносить.

## 4. Сохранность результата и публикации

- Полные исходные findings остаются в существующем JSON-артефакте. Markdown
  является представлением результата, а не новым источником истины.
- Не принимать произвольный model-generated `summaryMarkdown` как готовую
  доверенную разметку. Формировать chrome из валидированных findings/статуса.
- Сохранить marker в начале комментария, upsert/idempotency и existing
  revision/lifecycle protections. Этот план не добавляет inline comments:
  существующий GitHub summary publisher сейчас публикует только summary.
- Сохранить лимит 60 000 UTF-8 байт, экранирование HTML и недоверенных путей,
  нейтрализацию закрывающих details/summary и корректные code fences.
  Сокращать целые блоки с явным уведомлением, не обрезать HTML посередине.
  Зарезервировать место для состояния, критичных предупреждений и уведомления
  о сокращении. Длинное evidence не должно удалять сведения о неполном ревью.
- В исходном теле комментария подробности остаются обычным текстом/Markdown:
  агент, читающий body через API, не зависит от картинки и её OCR.

## 5. Необязательная картинка без отдельного хранилища

Добавить в существующий web application публичный GET endpoint, например:

```text
/review-banner/v1.svg?state=complete&critical=1&major=0&minor=0&info=0&lang=en&theme=dark
```

Endpoint не читает reviews, БД, GitHub, tenant credentials или private artifacts.
Он рисует произвольный общий баннер из разрешённых чисел и enum-параметров.
В URL и SVG не попадают review ID, repository, пользователь, путь, название
ошибки, исходный код или другой текст private PR. Поэтому endpoint может быть
доступен GitHub Camo без cookie/авторизации.

- Только allowlist `state`, `lang`, `theme`; целочисленные counts 0–9999.
  При числе вне диапазона publisher оставляет обычный Markdown без картинки.
  Невалидные параметры endpoint отклоняет; произвольного текста, URL,
  SVG-markup и внешних ресурсов не принимает.
- Чистая функция создаёт SVG примерно 640×110 CSS px: бренд, состояние,
  ненулевые счётчики. Использовать системные fonts и обычные SVG shapes/text,
  без scripts, foreignObject, remote fonts и image references.
- Ответ `Content-Type: image/svg+xml`, bounded body, `nosniff`, корректные
  cache headers и ETag. Версия в path фиксирует внешний вид; изменение шаблона
  получает новую версию URL. Старые ссылки не должны внезапно исчезать.
- Для светлой/тёмной темы разрешены две версии через `<picture>`; проверить
  sanitization GitHub на этапе canary. Рабочий `<img>` обязателен как fallback.
- Картинка необязательна и не заменяет текст состояния, детали или ссылки.
  Недоступность image endpoint не должна прерывать публикацию комментария;
  не добавлять обязательную сетевую загрузку баннера перед post/update.
- Первый image consumer только GitHub. GitLab сохраняет текстовый вариант
  до отдельной проверки своего рендерера.

SVG здесь удобнее WebP: текст и простые фигуры генерируются строкой и остаются
чёткими при масштабировании. Если позднее нужен именно WebP, тот же renderer
можно растеризовать на сервере; base64 внутри HTTP-процесса допустим как
внутреннее представление, но в GitHub Markdown всегда передаётся HTTPS URL.
Не добавлять сейчас rasterizer, image bucket и таблицу image artifacts.

## 6. Порядок реализации и проверки

1. На актуальных исходниках сделать этап компактного Markdown в существующих
   renderers. Обновить ценные существующие summary/publisher-тесты.
2. Проверить сценарии: одна critical; смешанные severity; 4+ findings;
   честный clean; providers failed; partial coverage; предыдущие активные
   threads без новых findings; dismissed; локализация; malicious HTML;
   длинный Unicode-результат; длинный code fence и evidence; повторная публикация
   обновляет прежний summary, а не создаёт ещё один.
3. Визуально проверить на GitHub desktop/mobile отсутствие повторов и потерянных
   важных предупреждений. Использовать существующий disposable test repository.
4. Image endpoint делать отдельным небольшим изменением после текстового этапа.
   Проверить enum/numeric validation, отсутствие пользовательского текста,
   MIME/cache/version, обе темы и согласованность counts с тем же входом,
   который получает Markdown renderer. Затем один GitHub canary с настоящим
   HTTPS URL, Camo и проверкой недоступного изображения.
5. Выполнить проверки и доставку затронутых репозиториев по
   [release operations](../operations/07-environments-and-release-management.md).
   Не считать обновление только SaaS доказательством обновления public Action.
   План сам по себе не является реализацией или deploy.

Предварительная оценка changed LOC с проверками: текстовый этап 180–350;
необязательный SVG endpoint и GitHub integration ещё 150–300. Это оценка
после исследования, не измерение готовой реализации.

## 7. Реализация

Компактные renderers, immutable source links, безопасный бюджет комментария и
необязательный HTTPS SVG реализованы. Настройка и повторяемый canary описаны в
[compact review comments](../operations/compact-review-comments.md).
Подтверждено также на настоящем PR: GitHub удаляет src у base64 WebP,
поэтому публикация использует HTTPS URL. Нативный текст остаётся полным.

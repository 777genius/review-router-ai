# Живые модели планов с ключом (GLM, MiniMax, Kimi) через код Sub2API

Статус: план v2 (учтено независимое ревью v1); реализация в трёх PR, деплой не входит.
Дата: 2026-11-17. Продолжает [64](64-gateway-native-ownership-and-model-catalog.md); правила владения те же, правило 4 из 64 для этих планов заменено (раздел 6).

## 1. Цель и границы

Пользователь планов GLM, MiniMax и Kimi выбирает модели из списка, который отдаёт провайдер. Логика остаётся в native и переиспользует код Sub2API. Платных ключей нет, реальных запросов к планам не делаем, проверка только на фикстурах. Пути `/models` у провайдеров для coding-ключей не подтверждены, поэтому сбой чтения не должен ухудшать то, что уже работает.

Входит: GLM, MiniMax, Kimi. Не входит: Grok (OAuth-custody), NVIDIA, OpenRouter, Codex.

## 2. Что переиспользуем

| Задача            | Готовое место                                                                                                                                          | Использование                                                                   |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| Ключ вне dispatch | `WithGatewayNativeQuotaCredential` (`native_gateway_quota_lease.go`): блокировка строки `FOR SHARE`, сверка scope и descriptor, ключ только в callback | вызывает только reader каталога                                                 |
| HTTP к провайдеру | клиент `GatewayProviderQuotaCollector`: без redirect, TLS 1.2+, лимит тела                                                                             | `FetchModels` рядом, тот же клиент, свой таймаут 2 секунды                      |
| URL списка        | `buildOpenAIModelsURL(base)`                                                                                                                           | база берётся из константы профиля в самом `FetchModels`, не из параметра вызова |
| Разбор            | `extractUpstreamModelIDsWithSelector(body, e -> e.ID)`                                                                                                 | только поле `id`, без подстановки `name`                                        |
| Кэш               | образец `gatewayModelsCache`                                                                                                                           | отдельное небольшое хранилище, см. 3.1                                          |

## 3. Решение

### 3.1 Native

1. `FetchModels(ctx, profile, credential)`: URL выводится из профиля, заголовок `Authorization: Bearer <ключ>` для всех трёх планов (как инференс и штатный запрос Sub2API к `/models`; правило «голый ключ» для GLM относится только к monitor-эндпоинту квот), таймаут 2 секунды, не-2xx, пустой список, битый JSON, редирект, тело больше лимита - ошибка. ID проходят `GatewayAccountModelIDValid`, дедуплицируются.
2. Хранилище `gatewayCodingPlanLive` в памяти, ключ - sha256 от scope и конверта ключа (как у OpenRouter), до 256 записей. В записи последний удачный список и время. Два срока: «свежий» 5 минут (для обновления в UI) и «для допуска» 24 часа. Неудачный fetch, включая `ForceRefresh`, не затирает последний удачный список. Не больше 2 живых fetch одновременно (try-acquire; при отказе сразу берётся то, что есть). Single-flight по ключу.
3. Каталог для профиля - всегда `snapshot`, никогда `unavailable`: `якорь`, затем статическая часть (GLM: `glm-5.3`; Kimi и MiniMax: пусто), затем живые модели в алфавитном порядке, без дублей, не больше 8 (текущий предел контракта Gateway; изменять контракт в этой поставке не нужно). Нет живого списка - каталог состоит из якоря и статической части. Возможности консервативные: `tools: function`, `reasoning: null`, `fast: null`.
4. Reader читает каталог по существующему маршруту `Read` (после `authorize`, с теми же проверками owner/generation до и после). Если запись «несвежая», берёт lease и вызывает `FetchModels`.
5. Допуск модели в запросе - одна функция: якорь, статическая часть или последний удачный живой список (срок для допуска 24 часа). Dispatch никогда не обращается к сети и не берёт lease: проверка по хранилищу только на чтение без ожидания (`peek`). После перезапуска native допускаются якорь и статическая часть, пока первое чтение каталога (UI или Gateway) не заполнит хранилище.
6. Места привязки (как в 64, но для всех трёх профилей; предикат «профиль с каталогом» становится истинным для GLM, MiniMax, Kimi):
   - `gatewaytransport/http.go:111,122-127`: до `h.reserve` только структурная проверка ID; членство проверяет native dispatch (как у OpenRouter);
   - `native_gateway_provider_responses.go:136-139`: структурная проверка для этих профилей;
   - `native_gateway_identity.go:299-300` и финальная граница (`:500-506`): членство через `peek`; результат допуска хранится в состоянии dispatch (как `requestedModel`);
   - `GatewayAccountModelsReader.Read`: ветка этих профилей;
   - `GatewayNativeCodingPlanProfileValid` остаётся только про якорь.

### 3.2 Gateway

В `accountModelDiscoveryProfiles` добавить Kimi и MiniMax (`native_catalog`). Остальное без изменений: native всегда отвечает `snapshot` с 1..8 моделями, поэтому `unknown` возникает только при недоступности native, как и для других профилей.

### 3.3 ReviewRouter

Поставка: архив SDK из слитого Gateway, provenance, lockfile, `conversation-source-stamp` (требует повторной квалификации conversations при деплое); тесты checkout и readiness для Kimi и MiniMax.

## 4. Вне объёма

Метаданные моделей из `models.dev`; фильтр списка провайдера по документации плана; фоновый сборщик и кэш в БД; расширение контракта Gateway за 8 моделей (потом отдельным шагом: сначала контракт у потребителей, затем native); Grok.

## 5. Проверка без платных ключей

- Go (`-tags unit`), фикстура провайдера на `httptest`: успех (якорь первым, статическая часть, дубли и якорь в ответе провайдера, предел 8, детерминированный порядок), не-2xx, пустой список, битый JSON, редирект, тело больше лимита, таймаут больше 2 секунд, заголовок `Bearer`; свежий кэш не вызывает провайдера повторно, `ForceRefresh` вызывает; неудачный fetch сохраняет последний удачный список; семафор на 2 fetch; допуск: модель из списка проходит, вне списка и вне статической части отклоняется на admission и на финальной границе (проверка мутацией); dispatch не делает сетевых вызовов и не берёт lease; ключ не попадает в ответ и лог.
- Gateway: контракт принимает снимки Kimi и MiniMax, discovery только у этих трёх профилей.
- RR: параметризация checkout и readiness.

## 6. Документы и риски

- В `ACCOUNT_GATEWAY_OWNERSHIP.md`, `AGENTS.md` и комментарии `native_gateway_model_catalog.go` правило 4 из 64 («модель попадает в каталог только с доказательством принадлежности к плану») для этих планов заменяется решением владельца: список даёт провайдер, статическая часть остаётся нижней границей.
- **Не проверено на реальных хостах:** путь `/models` и схема заголовка у `api.z.ai`, `api.minimax.io`, `api.kimi.ai`. При любой ошибке работает якорь и статическая часть.
- **Список провайдера не доказывает принадлежность к плану:** запрос к модели вне плана получит ошибку провайдера; «Проверить подключение» покажет только категорию отказа.
- **Порядок деплоя:** native, затем Gateway (добавляет discovery Kimi и MiniMax), затем RR. Если Gateway выкатить раньше native, старый native ответит `unsupported`, и Kimi и MiniMax потеряют допуск якоря. Откат в обратном порядке. На prod подключён 1 Kimi, поэтому порядок соблюдать.
- Смена SDK меняет `conversation-source-stamp`.

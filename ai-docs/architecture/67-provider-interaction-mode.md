# Режим взаимодействия ревьюеров: вместе или по очереди

Статус: план v5 (учтено ревью поставки 2) - поставка 2 (настоящее переключение) поверх влитой поставки 1 ([#890](https://github.com/777genius/review-router-ai/pull/890)). Деплой не входит.
Дата: 2026-11-17. Меняет для режима fallback правило «не продвигать соседа и не выбирать запасную модель» из [плана нескольких ревьюеров](../plans/2026-10-28-gateway-multi-reviewers.md): запасной ревьюер запускается только по явному выбору пользователя. Классы сбоев и исключения покрытия берутся у [69](69-provider-quota-nonfatal.md) (квота), без второго классификатора.

## 1. Исходное состояние

- Политика хранит упорядоченный `providers`; runtime-конфигурацию (schema 3) строит `resolveEffectiveReviewPolicy`. Индекс 0 - primary (описание PR, lifecycle).
- Несколько ревьюеров в прогоне - только all-Gateway: снимок v4 (`captureMultiple`) ставит каждому `required: true`, план `REVIEW_ROUTER_REVIEWER_PLAN_JSON` исполняет runtime `RunT0ReviewOrchestration` (lane на ревьюера).
- Сбой посреди прогона (таймаут, 429, auth, модель) видит только runtime. SaaS-финализатор `deriveCoverageState` требует satisfied каждого required-слота; 69 добавляет проверяемые сервером исключения (`coverageExceptions` из `ProductionFinalizationFactsAdapter`).
- Старый runtime молча применяет незнакомые env-ключи (`isSafeRuntimeEnvKey` - запрет, а не список), а парсер плана v1 строгий. Значит режим можно передать только через план новой версии и только продюсеру, который её объявил.
- Поставка 1 (на main, не задеплоена): режим `providerMode` хранится рядом со списком, редактор с селектом и порядком; в fallback запускается только первый.

## 2. Модель

- Хранение, наследование и запись - как в поставке 1: в документе хранится только `"fallback"`, режим принадлежит списку, все писатели его сохраняют, смена режима проходит авторизацию и аудит.
- Runtime-конфигурация теперь несёт весь список: `providers` в порядке пользователя и `providerMode: "fallback"` (только при 2+ ревьюерах; parallel и одиночный список байт-в-байт прежние). Инварианты в `reviewConfigurationSchema`: fallback ⇒ `providerMaxParallel = 1`, `inlineMinAgreement = 1`, все ревьюеры `codex_account_gateway` (последовательно их исполняет только план v4). Сохранённые parallel-лимиты остаются в документе.
- `rosterConfig` из поставки 1 убирается: `config` снова содержит всех ревьюеров, `selections[i]` совпадает с `config.providers[i]`, проверки при записи идут по `config`.
- Снимок v4 получает необязательное поле `providerMode: "fallback"`; его ставит `captureMultiple` из конфигурации.

## 3. Протокол и gate

- `reviewerPlanContract`: `planVersion: 2`, новый дескриптор и digest. План v1 (parallel) не меняется ни по форме, ни по байтам; план v2 = v1 + `providerMode: "fallback"`. Парсер принимает обе версии. Старый runtime план v2 отвергает (`review_reviewer_plan_invalid`), ансамбль невозможен.
- Профиль продюсера: `{ planVersion: 1, descriptorDigest: <v1> }` (исторический digest сохраняется константой) или `{ planVersion: 2, descriptorDigest: <v2> }`. Несколько ревьюеров допускает любой из двух; fallback - только v2. Генератор пишет в манифест Action профиль v2.
- Admission: fallback-список при продюсере без v2 даёт отказ `reviewer_fallback_unsupported` (422 `review_run_authorize:reviewer_fallback_unsupported`), а не тихий запуск. Промежуточного «только первый» больше нет.
- БД: CHECK профиля продюсера (`000152`) допускал только `planVersion: 1`. Миграция `000159_producer_reviewer_plan_v2` расширяет его до 1 и 2; она зарегистрирована в schema handoff (checkout164, как 158 из 69). Self-hosted installer тоже принимает профиль v2.
- Checkout строит план v2 для fallback-снимка; `maxParallelReviewers = 1`.

## 4. Семантика выполнения (runtime)

- Lanes идут строго по порядку плана, по одному. Lane «принят», если у него есть required-слоты и все они приняты (необязательные lifecycle-задачи не решают); тогда остальные не запускаются и локально помечаются `fallback_unused`.
- Причину остановки lane несёт `ReviewScopedInvocationFailure.stopReason` (класс `ProviderInvocationFailureClassifier` или исчерпание слота). Переход только по allow-list: `CapacityUnavailable` (квота, 429), `AuthenticationUnavailable`, `ConfigurationMismatch` (недоступный ревьюер: нет allocation, модели, движка), `Retryable` со scope `allocation` и `AttemptBudgetExhausted` (у Gateway бюджет 1 попытка: таймаут запроса или неверный вывод).
- Всё остальное - стоп без перехода (fail-closed): `AdmissionLimited` (значение совпадает у класса и причины исчерпания, их не различить), отложенное расследование, дедлайн прогона, `ProviderLaneBusy`, `NotRunnable`, неизвестная причина, scope `run`, отмена, смена ревизии.
- Сбой со scope `allocation` останавливает все ревьюеры этой allocation: запасной на том же аккаунте не запускается, цепочка идёт к следующей allocation.
- Покрытие: если какой-то ревьюер принят, упавшие раньше становятся необязательными в проекции (`required: false`, они остаются в счёте «N of M failed»), а неиспользованные из проекции убираются. Принятые результаты упавших не выбрасываются, согласие 1. Пропуск по квоте из 69 в fallback не считается: правило цепочки первично. Если не принят никто - required-слоты всех ревьюеров считаются, ревью неполное.
- Finalize шлёт `allowPartial: true` при использованной цепочке и затем читает решение сервера (как 69).
- Описание PR и lifecycle по-прежнему у primary (первого); если он не смог - эти необязательные задачи не выполняются.

## 5. Покрытие на сервере

- `ProductionFinalizationFactsAdapter` добавляет в `coverageExceptions` `orderedFallbackVotes` - голоса ревьюеров снимка v4 с `providerMode: "fallback"`.
- `deriveCoverageState`: кроме правила 69, ревью полное, если голос цепочки имеет required-слоты и выполнил их все, каждый открытый required-слот принадлежит голосу цепочки и не `leased`, и проекция сама заявляет полное покрытие. Заявка проекции только сужает. Всё упало - `partial`. Незапущенные слоты остаются `pending`, finalize их отменяет.
- Порядок цепочки сервер не проверяет: покрытие обеспечивает принятый ревьюер, которого выбрал пользователь.

## 6. UI

- Подсказка fallback: «Reviewers run one at a time, top to bottom. The next one starts only when the one above it can't finish the review because of quota, sign-in, a timeout or an unavailable model.» Оговорка «not available yet» снимается: путь закрыт gate и работает с продюсером v2.
- Форма настроек репозитория в fallback тоже скрывает parallel-лимиты.

## 7. Совместимость и порядок раскатки

- Миграция `000159` (расширение CHECK, совместима с текущими строками). Новые поля: `providerMode` в runtime-конфигурации и снимке v4 (только fallback).
- Откат: до регистрации v2-продюсера откат SaaS безопасен. После - старый код не читает строку v2-продюсера и отвергает его план; поэтому сначала вернуть канал `workflow-v1` на последний v1-продюсер, затем откатывать SaaS, или только вперёд.
- Порядок: SaaS #888 (миграция 158) → SaaS поставка 2 (159, парсеры v1/v2, gate) → экспорт протокола из влитого SaaS и релиз runtime (#394 + fallback) → регистрация v2-продюсера → промоут `workflow-v1`. До регистрации fallback-списки из 2+ ревьюеров получают отказ admission; parallel не затронут. Поставку 1 (#890) без поставки 2 не деплоить.
- Зависимость: исключения покрытия 69 (#888, runtime #394). Поставка 2 строится поверх них и вливается после них.

## 8. Проверка

- SaaS: схема и материализация (весь список, режим, инварианты), gate admission (v1-продюсер - отказ, v2 - снимок с режимом), план v2 и парсер v1/v2, `deriveCoverageState` (принят второй, принят первый и остальные не начаты, все упали, `leased`, заявка без факта), профили продюсера.
- Runtime: оркестрация (переход по квоте, auth, недоступности, исчерпанию попыток; стоп по `AdmissionLimited`; первый принят - второй не стартует; все упали), проекция, парсер плана v2. Пересобрать `dist`.
- Postgres и E2E - в CI.

## 9. Вне объёма и риски

- Смешанные цепочки Gateway + direct, env-путь (`core/orchestrator.ts`), веса и отдельные таймауты.
- Время: запасной ревьюер запускается после сбоя первого в том же бюджете прогона. Таймаут одного запроса переводит к следующему, но ревьюер, исчерпавший весь дедлайн прогона, даёт стоп (`DeadlineReached`).
- Бюджет слотов `planReviewerSlotBudgets` делится между всеми ревьюерами цепочки; на очень больших PR принятый запасной получит меньше слотов.
- До регистрации продюсера v2 выбор fallback для 2+ ревьюеров останавливает ревью отказом admission.
- Сводки в списке провайдеров режим не показывают.

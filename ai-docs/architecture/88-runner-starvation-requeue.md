# Ревью не стартует без раннера GitHub: прогон остаётся в очереди, а не отменяется (2026-11-21)

Статус: план v4 (учтены независимые ревью 1, 2 и 3). Реализация: RR worker, [PR #955](https://github.com/777genius/review-router-ai/pull/955). Релиз Action и деплой не входят.
Источник: read-only выборки из БД RR (`ReviewRequestedIntent`, `ReviewExecutionV2`), GitHub API (прогоны, job и раннеры активных репозиториев аккаунта `777genius`), код `recover-review-requested-dispatches.ts`, `review-requested-intent.ts`, `prisma-review-requested-intent-store.ts`, `review-v2-intent-dispatcher.ts`, `review-v2-dispatch-cleanup-handler.ts`, прогресс-комментарий в worker. Продолжает пункт M плана [87](87-nvidia-large-pr-stability.md). В названии "requeue" значит "остаётся в очереди", повторной отправки нет.

## Что видно на prod

Окно то же, что в плане 87: запросы, созданные с 2026-11-17 13:24 до 2026-11-20 19:48 UTC.

- Ревизия этих запросов потом не проверялась ни разу у 140 из 141. Следующий запрос на тот же PR пришёл в течение 30 минут после отмены у 53, позже у 69, никогда у 16.

## Механизм

1. Worker отправляет `workflow_dispatch` и переводит запрос в `awaiting_authorization` со сроком `resolutionDeadlineAt` = время отправки + `REVIEW_ROUTER_REVIEW_V2_INTENT_AUTHORIZATION_TIMEOUT_MS` (30 мин по умолчанию).
2. Каждые ~30 с `RecoverReviewRequestedDispatches.resolveAwaitingAuthorization` читает прогон (`inspectKnownRun`). Пока прогон не завершён, это `Pending`, и проверка откладывается до срока.
3. На сроке запрос становится `terminal` / `authorization_deadline_exceeded`, outbox `review.requested_dispatch_cleanup` отменяет прогон. Повтора нет: повтор #742 (до 3 попыток) срабатывает только для прогона, который завершился с `failure`, `timed_out` или `startup_failure`.
4. RR не различает "job ждёт раннер" и "job запущен, но не дошёл до авторизации". Для него оба случая `Pending`.

Срок нужен, чтобы запрос сходился: окно, в котором прогон может получить авторизацию, ограничено, и тот же PR не держит "висящий" запрос. Пока окно открыто, событие PR на ту же ревизию присоединяется к ждущему прогону (`joinsDispatchedRun`), а новый запрос PR не берётся в работу (`laneBusy`). Срок не задаёт время жизни выданной авторизации: у неё свой срок (`ReviewRunAuthorization`), план его не трогает. Авторизация при выдаче заново сверяет ревизию с GitHub.

## Решение: прогон ждёт раннер в своей очереди (DO)

Перед сроком, если прогон всё ещё ждёт раннер, worker даёт запросу ещё одно окно того же прогона. Повторной отправки нет.

1. Когда: в последние 4 прохода восстановления до срока (около 2 минут, но не больше четверти окна, чтобы длинный интервал проходов не превратил проверку в продление сразу после отправки). Уже прошедший срок не продлевается никогда: после него на ту же ревизию мог прийти и уйти в работу новый запрос, и тогда прогонов стало бы два.
2. Условия, все сразу, по свежим данным GitHub:
   - попытка прогона не завершена, у неё есть хотя бы один job, каждый job в статусе `queued`, ни одному не назначен раннер (`runner_id` 0 или пусто, `runner_name` пусто, нет начатых шагов). Job, который ждёт одобрения environment, не считается;
   - PR открыт, его head и base совпадают с ревизией запроса;
   - запрос ещё не допущен (`admission` = `not_evaluated`, нет авторизации и исполнения);
   - у PR нет другого запроса, который ждёт свой прогон (например, ручной `/rr review` на той же голове: он не присоединяется к ждущему прогону). Иначе после раннера у ревизии было бы два прогона; запрос закрывается в срок, как раньше, и уходит ручной.
3. Сколько: новый срок = текущий срок + обычное окно (30 мин), но не позже отправки + 90 минут (константа в домене `reviewRequestedMaxQueuedRunWaitMs`, без нового env и флага). Продление короче половины окна не делается: раннер, пришедший в такой огрызок, всё равно не успеет к допуску. С окном 30 минут это ровно два продления: 30, 60, 90 минут. Это правило - одна чистая функция домена (`reviewRequestedQueuedRunWaitExtension`), её же use case проверяет до обращения к GitHub.
4. Как: переход `extendReviewRequestedQueuedRunWait` в домене, проверка версии и времени по часам БД, в той же блокировке PR (`lockScope`), что у остальных переходов диспетчеризации. Предел считается по сохранённому `submissionStartedAt`: новая колонка и миграция не нужны.
5. Любая ошибка чтения GitHub, неполный или странный ответ, закрытый PR, новая голова, job не в `queued`: продления нет, на сроке работает прежний путь (терминал, отмена прогона). Продление требует положительного доказательства.
6. Что не меняется:
   - вытеснение пушем: новая ревизия по-прежнему вытесняет ждущий запрос (он ещё не допущен), outbox отменяет его прогон;
   - событие PR на ту же ревизию присоединяется к ждущему прогону, пока окно открыто; второго прогона нет;
   - прогон, который получил раннер, но не дошёл до авторизации, заканчивается на своём сроке как раньше;
   - срок жизни авторизации, правило "неизвестный эффект закрывает прогон", допуск по размеру, повтор #742.

Раннер, пришедший после проверки, получает не больше одного окна плюс 2 минуты. Раннер, пришедший между чтением GitHub и записью в БД (секунды), тоже получает продлённое окно, то есть до ~32 минут. Это окно до первой авторизации, а не срок жизни авторизации; уже выданная авторизация не меняется.

Почему ждать, а не отправлять заново: очередь общая для аккаунта. Новый прогон может обогнать ждущий, только если GitHub раздаёт раннеры в обратном порядке, а это неправдоподобно (порядок GitHub не документирует, по замерам похоже на очередь по порядку постановки). Новый прогон встал бы в конец очереди глубиной 37-104 минуты и почти наверняка снова не дождался бы раннера, а каждая отмена и отправка тратит общий бюджет попыток #742.

## Что видит пользователь

Оба статуса пишутся в единственный прогресс-комментарий PR (маркер `review-router-live-progress`), тем же шлюзом, что живой прогресс: он проверяет голову PR, находит комментарий приложения и правит его на месте или создаёт. Новых комментариев нет. Как только прогон стартует, его живой прогресс перепишет статус.

1. После первого продления (около 28-й минуты): "**Phase:** Waiting for a runner. The review of commit `abc1234def56` has been waiting for a GitHub Actions runner since 2026-11-21 13:28:24 UTC. It starts by itself when GitHub assigns one. ReviewRouter keeps it queued until about 2026-11-21 14:58:24 UTC." Время конца - предел (отправка + 90 мин), абсолютное: устаревший текст виден сам по себе.
2. Запрос закрылся по сроку, прогон до ReviewRouter не дошёл: "**Phase:** Not started. The review of commit `abc1234def56` did not start: GitHub Actions did not give the review job a runner within N minutes. To try again, push a new commit or re-run the ReviewRouter run." Если GitHub успел дать раннер, но job не дошёл до авторизации (раннер пришёл слишком поздно или job упал раньше), причина нейтральная: "the review job did not reach ReviewRouter within N minutes." Закрытие по сроку всегда получает свой статус и заменяет "Waiting". N берётся из фактов запроса (от отправки до срока), а не из константы: запрос мог закрыться и на 30-й минуте.

Совет про re-run верен: запрос в `terminal` может стать основой новой попытки прогона (`reviewRequestedIntentCanSeedRerun`), запрос для попытки 2 создаётся, когда job уже стартовал, и его срок считается от этого момента. Такой re-run тоже ждёт раннер в очереди, но наш срок его не отменит.

Как это устроено:

- Outbox `review.requested_start_notice` (коды ошибок в allow-list outbox) с видом статуса ставится в той же транзакции, что первое продление (повторные продления дубля не ставят) и закрытие по сроку.
- Обработчик молчит, если репозиторий или прогон пропали (404, недоступный репозиторий, непонятный ответ GitHub): сказать нечего. Повторяет только сбой GitHub; ошибки БД уходят в outbox как есть, сигнал прав БД сохраняется.
- Обработчик молчит, если запрос уже не в том состоянии, о котором статус (прогон дошёл до авторизации, запрос закрыт или удалён), если на PR появился более новый запрос ревью (кроме событий, присоединённых к этому), если PR сменил голову или закрыт, если комментарии прогресса выключены (`REVIEW_ROUTER_HOSTED_PROGRESS_COMMENT_WRITES`, список репозиториев). "Waiting" ещё требует, чтобы все job были в очереди без раннера.
- Запись делит с живым прогрессом бюджет установки и cooldown после rate limit (один общий хелпер), берёт известный `commentId` PR и ждёт повтором outbox, пока у публикации прогресса этого PR есть живой claim или неопубликованная версия. Так статус не перепишет прогресс, который как раз публикуется. Повторов 20, с backoff outbox это около часа; потом событие уходит в dead letter, на PR остаётся прежний текст.
- Текст живёт в `review-progress` рядом с обычным форматтером, запись в worker рядом с публикатором прогресса.

## Риски

- Нагрузка: ревью, которые раньше отменялись, теперь получают раннер и держат его 5-80 минут. Около 40 прогонов в день в прошлом окне. CI аккаунта будет ждать дольше. Это цена ревью, которое пользователь ждёт.
- Ревью приходит позже: до 90 минут ожидания плюс само ревью. Новый пуш за это время как и раньше вытесняет запрос. Во втором замере p90 ожидания 104 минуты: часть запросов не дождётся и 90 минут, они получат статус "Not started".
- Ручной `/rr review` на той же голове, пока прогон ждёт: ждущий запрос больше не продлевается, закрывается в свой срок, и уходит ручной (как раньше, до 30 минут ожидания). Ручная команда сама идёт через workflow, которому тоже нужен раннер.
- "Waiting" остаётся, если запрос закончился не закрытием по сроку, а иначе: отказ по размеру PR после прихода раннера (API пишет рядом свой комментарий о лимите), новый пуш (до ~28 минут, пока новый запрос не стартует или не получит свой "Waiting"), отмена до допуска, исчерпанные повторы #742 (`dispatch_attempts_exhausted`), ручная отмена прогона. Текст тогда показывает уже прошедшее "until about ...". Отдельного статуса для этих случаев нет; закрытие статусом при отказе по размеру - возможный follow-up.
- Перезапуск worker на сроке: если worker пропустил последние 2 минуты окна, запрос закроется как раньше. Прошедший срок не продлевается сознательно.
- Гонка в последние секунды перед пределом 90 минут: раннер, пришедший туда, не успеет к допуску (нужно не меньше 30 с до срока). Так же, как сейчас на 30-й минуте.
- Статус может переписать прогресс нового ревью, если оно опубликуется между проверками обработчика и записью (секунды, несколько вызовов GitHub). Защиты: пока окно открыто, новый запрос того же PR не уходит в работу (`laneBusy`), проверка более нового запроса, проверка головы в шлюзе, ожидание публикации прогресса. Следующее обновление прогресса нового ревью перепишет текст.
- Запросы GitHub API: обычное чтение прогона раз в ~30 с теперь идёт до 90 минут вместо 30 (около 180 чтений на голодающий запрос вместо 60); проверка перед сроком добавляет 2 чтения (job попытки и PR) до 4 раз на окно и только пока продление ещё возможно; каждый статус стоит 2 чтения проверки и 2-7 чтений и одну запись в шлюзе прогресса (голова PR, поиск комментария).

## Тесты (только рискованное)

- Домен продления: прошедший срок не продлевается, предел соблюдается (не дальше отправки + 90 мин), огрызок короче половины окна не даётся, ждущий ручной запрос PR блокирует продление, чужая версия, не тот статус, уже допущенный запрос, авторизация или исполнение есть.
- Use case: продление только при "все job в очереди без раннера" + "ревизия текущая" и только в последние проходы до срока; при раннере, job не в `queued`, закрытом PR, новой голове, ошибке GitHub продления нет и запрос закрывается в срок как раньше; после предела закрытие с `authorization_deadline_exceeded`; ровно два продления при окне 30 мин.
- Prisma store (реальная БД): продление сохраняется под блокировкой PR и не нарушает `resolution_window_check`; устаревшая версия (вторая реплика) и ждущий ручной запрос получают отказ; статус "waiting" ставится один раз на несколько продлений, "not started" один раз вместе с закрытием.
- Шлюз GitHub: разбор job (0 job, страница не полная, раннер назначен, начатый шаг, `waiting` вместо `queued`, чужой прогон или попытка).
- Обработчик статуса: молчит при новом запросе, при сменившемся состоянии запроса, при сдвинутой голове, при выключенных комментариях; "waiting" молчит при раннере; "not started" с раннером пишет другую причину; ждёт при занятом прогрессе.
- Резерв записи статуса: ждёт при claim или неопубликованной версии прогресса PR, при cooldown и интервале установки, иначе берёт одну запись и известный `commentId`. `hasNewerRequestInScope` на реальной БД: присоединённое событие той же ревизии не считается, ручной запрос считается.

## Выкатка

Только образ RR (worker). Action, workflow, схема, миграции и env не меняются, порядок native -> Gateway -> RR -> Action не затронут. Едет в следующем бандле. Откат: прежний образ worker; события `review.requested_start_notice`, которые старый worker не знает, остаются в outbox без обработчика и ничего не делают. Запись в реестре: [2026-11-21-runner-starvation-requeue](../deployments/2026-11-21-runner-starvation-requeue.md).

## Что нужно от владельца

Голод раннеров лечится только снаружи RR: свой раннер для job ReviewRouter (или для тяжёлого CI), другой план GitHub с большим лимитом job, меньше CI в universal-agent-plugins, review-router-ai и agent-teams-ai. Это изменение превращает "ревью не пришло" в "ревью пришло позже" и честный статус на PR, пока ждёт и если не пришло совсем. История дашборда по-прежнему показывает такой запрос как "Failed"; отдельный статус там - отдельное решение.

# Живой список моделей NVIDIA Build, предел каталога и ручной ввод модели

Статус: план v2 (учтено независимое ревью v1); реализация в трёх PR (native, Gateway, RR), деплой не входит.
Дата: 2026-11-17. Продолжает [64](64-gateway-native-ownership-and-model-catalog.md) и [65](65-live-coding-plan-model-catalog.md); правило 4 из 64 для NVIDIA заменено решением владельца (раздел 6).

## 1. Цель и границы

NVIDIA Build показывает все подходящие для ревью модели из публичного списка провайдера, а не одну. Списком владеет native (один источник для Gateway и RR). Модели, не предназначенные для ревью, отсекаются. Предел 8 моделей у каталога убирается по всей цепочке контрактов, остаётся технический предел 512. В RR модель можно выбрать из списка или ввести вручную.

Факт (проверено 2026-11-17): `GET https://integrate.api.nvidia.com/v1/models` без ключа отвечает 200, 32 модели, только поля `id`, `object`, `created`, `owned_by`; метаданных о типе модели нет.

Входит: NVIDIA, предел каталога для NVIDIA и планов GLM/MiniMax/Kimi, ручной ввод в RR. Не входит: раздел 7.

## 2. Что переиспользуем

| Задача            | Готовое место (native, `backend/internal/service`)                                          | Использование                                                                   |
| ----------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Хранилище и кэш   | `GatewayCodingPlanLiveModels` (`native_gateway_live_models.go`)                             | 5 минут свежести, 24 часа для допуска, backoff 1 минута, 2 fetch, single-flight |
| HTTP              | клиент `GatewayProviderQuotaCollector`: без redirect, TLS 1.2+, лимит тела 256 КБ           | `FetchModels`, таймаут 2 секунды                                                |
| URL и разбор      | `buildOpenAIModelsURL`, `extractUpstreamModelIDsWithSelector` (только `id`)                 | база - константа `GatewayNVIDIABuildBaseURL`, не из аккаунта и не из запроса    |
| Каталог и допуск  | `gatewayCodingPlanCatalogue`, `gatewayCodingPlanAdmitted`, `readStaticCatalogAccountModels` | NVIDIA - ещё один профиль с каталогом «якорь, статика, живой список»            |
| Проверка формы ID | native `GatewayAccountModelIDValid`, RR `gatewayModelSchema`                                | на всех границах и в поле ручного ввода                                         |

Имена с `CodingPlan` в общем коде становятся нейтральными (`GatewayLiveModels`, `GatewayModelCatalogProfile` и т. п.). `GatewayNativeCodingPlanProfileIDValid` не трогаем: он выбирает протокол Responses, а NVIDIA остаётся на мосте Chat.

## 3. Native

1. Источник списка задаёт профиль: GLM, MiniMax, Kimi - свой base URL и ключ из lease; NVIDIA - `GatewayNVIDIABuildBaseURL`, список публичный. Для публичного источника `FetchModels` не принимает ключ (переданный ключ - ошибка) и не ставит `Authorization`. Lease и расшифровка ключа для NVIDIA не вызываются, второй границы custody нет.
2. Запись хранилища NVIDIA одна на процесс (ключ - константа профиля): список одинаков для всех аккаунтов. Заполняет её только чтение каталога после `authorize` (UI или Gateway). Ключевые планы, как и раньше, - запись на зашифрованный аккаунт. Общая запись не бывает «произвольной жертвой» при вытеснении из полного хранилища.
3. Принудительное обновление выполняется не чаще раза в минуту на запись (для всех источников): частые «Обновить» не занимают общие 2 слота.
4. Фильтр «не для ревью» - одна функция в `native_gateway_model_catalog.go` для всех живых списков (NVIDIA и планы): ID исключается, если содержит (без учёта регистра) маркер `embed`, `rerank`, `retriev`, `guard`, `shield`, `safety`, `reward`, `clip`, `detect`, `translat`. Подстрока, а не токен: так ловятся `nemoguard`, `nvclip`, `nemoretriever`. Маркеры, а не список ID: новые модели тех же семейств отсекаются без правки кода. Якорь и статика фильтром не трогаются. Фильтр стоит до сортировки и обрезки, поэтому отсечённые ID не занимают места в пределе. На текущем списке NVIDIA остаётся 18 из 32. Каждое чтение пишет в лог строку с числами и отсечёнными ID (без ключа и тела).
5. Каталог NVIDIA: якорь `nvidia/nemotron-3.5-super-vl-120b-a12b` (статика и нижняя граница), затем живой список по алфавиту без дублей; источник в ответе остаётся `nvidia`. Возможности консервативные, как у планов: `tools: function`, `reasoning: null`, `fast: null`. Нет списка (сбой, перезапуск) - каталог из якоря.
6. Предел: `gatewayLiveModelsMax = 512` вместо 8 - для ответа провайдера и для каталога. 512 записей - до ~120 КБ JSON при лимитах 2 МБ у Gateway (клиент native и ответ facade) и у всех клиентов RR, читающих модели (`accountModelCatalogResponseBytes`).
7. Допуск модели NVIDIA - та же функция, что у планов: якорь, статика или последний удачный живой список (до 24 часов), только память, без сети и lease. Места привязки:
   - `gatewaytransport/http.go:122`: NVIDIA читает `model` из payload, проверка структурная (сейчас - только якорь); метка usage берётся из того же значения;
   - `native_gateway_provider_responses.go:132`: структурная проверка вместо `GatewayNVIDIABuildModelValid` (функция удаляется);
   - `native_gateway_identity.go:299-300,380-388` и финальная граница `:506-512`: членство через общую функцию;
   - `GatewayAccountModelsReader.Read`: NVIDIA и планы - одна ветка.

Не меняются: якорь в descriptor, enrollment (`handler/admin`), `GatewayNativeAPIKeyProfileValid`, конфиг bootstrap, мост Chat у NVIDIA.

## 4. Gateway

`accountModels` в `facade-client/contracts`: у `nvidia` `.length(1)` заменить на `.min(1).max(512)`, у `native_catalog` `.max(8)` на `.max(512)`, одна именованная константа. Остальное без изменений: схема возможностей `nvidia`, discovery-профили, `accountModelAdmission` (у NVIDIA при `unavailable` пусто), строгие поля запроса для `nvidia`, `#publicRequestedModel` (у NVIDIA есть discovery). README SDK и `AGENTS.md`: NVIDIA - живой список native.

## 5. ReviewRouter

1. Архив SDK из слитого Gateway во всех трёх потребителях, provenance, lockfile, `conversation-source-stamp` и verifier - как в PR #879.
2. Ручной ввод: поле модели у провайдеров Gateway - combobox (выбор из списка или ввод с фильтром). В диалоге настройки и в списке провайдеров он уже есть; в ростере ревьюеров простой select заменяется на него. Введённое значение проверяется `gatewayModelSchema`: неверная форма - сразу понятная ошибка; форма верна, но модели нет в списке аккаунта - сообщение, что провайдер не перечисляет эту модель, с советом выбрать из списка или обновить его. Сохранить такую модель нельзя (и сервер RR отвечает `gateway_review_model_unsupported`).
3. Правило допуска введённой вручную модели (решение): то же, что у других живых каталогов через Gateway (планы, OpenRouter): модель допускается, только если она есть в каталоге аккаунта, который публикует native. Ввод вручную каталог не обходит. Почему не «пропускать любую валидную форму к провайдеру»: (а) это обходит фильтр «не для ревью»; (б) ломает инвариант Gateway «допуск только из снимка»; (в) отказ провайдера после входа в него виден как `effect_unknown`, а не как понятная ошибка. Понятный отказ даёт каталог, до провайдера: в UI, на сервере RR, в Gateway и в native. Ревью подтвердило, что обхода нет (валидация конфигурации, checkout, Gateway facade, probe).
4. Тесты: options NVIDIA с длинным списком; сообщения поля (неверная форма, нет в списке, выбор по точному вводу).

## 7. Вне объёма

Метаданные моделей из `models.dev`; проверка tools по каждой модели; фоновый сборщик и кэш в БД; живой список Grok; допуск моделей вне списка провайдера; изменение trial-ограничений NVIDIA в RR (синтетический checkout, запрет conversations); автовыбор модели по умолчанию при нескольких моделях (как у GLM сейчас).

## 8. Проверка

- Native (`-tags unit`, фикстура `httptest`): запрос NVIDIA без `Authorization`, путь `/v1/models`; фильтр на реальных ID NVIDIA; якорь первым, сортировка, дубли; одна запись на все аккаунты NVIDIA; ключ для публичного источника и отсутствие ключа для ключевого отклоняются без сети; предел 512 (600 ID у провайдера - 512 в каталоге, допуск ровно по опубликованному); принудительное обновление не чаще раза в минуту; общая запись переживает вытеснение; сбой сохраняет последний удачный список; допуск NVIDIA и GLM: из списка - транспорт, admission и финальная граница проходят, вне списка - отказ до провайдера и до блокировки строки.
- Реальная проверка: однократный прогон того же `FetchModels` и чтения каталога против настоящего `integrate.api.nvidia.com` (только GET списка, без ключа и инференса); тест не коммитится.
- Gateway: контракт принимает 512 моделей `nvidia` и `native_catalog`, отклоняет 513, дубли и неверные ID.
- RR: typecheck, eslint, prettier, vitest затронутых пакетов.

## 9. Порядок слияния, деплоя и отката

- Слияние: native, Gateway, RR (архив SDK собирается из слитого Gateway).
- Главное правило деплоя: native с этим изменением выкатывается последним, когда Gateway и RR уже принимают длинный снимок. Иначе старый Gateway (`length(1)` у NVIDIA, `max(8)` у планов) не разберёт ответ, получит `unknown`, и NVIDIA потеряет все модели, включая якорь; так же планы с живым списком длиннее 8. Старый RR тоже отклонит длинный снимок своим SDK.
- На 2026-11-17 по реестру деплоя на prod Gateway 108 и native 98, то есть 64/65 ещё не выкачены, а для них нужен порядок native, Gateway, RR. Совместный безопасный порядок: native на коммите слияния #100 (без 68), затем Gateway с 68, затем RR с 68, затем native с 68. Если 64/65 уже выкачены отдельно: RR, Gateway, native.
- Откат обратный: native, затем Gateway, затем RR. После отката native сохранённые модели NVIDIA вне якоря и модели планов сверх статики отклоняются при checkout (`gateway_model_settings_unavailable`), пока их не сменят.
- Смена SDK меняет `conversation-source-stamp`: деплой RR согласовать с повторной квалификацией conversations (как в 64/65).

## 10. Риски

- Возможности моделей не проверены: модель без function calling или с другим форматом ответа получит ошибку провайдера уже после входа в него (`effect_unknown`). Протокол Responses->Chat и `ProviderTokenUpperBound` квалифицированы только на якоре.
- Фильтр по маркерам может пропустить узкую модель (сейчас `bigcode/starcoder2-15b`; возможны `bge`, `ocr`, `asr`, `tts`) или, реже, отсечь нужную; правится в одном месте, лог показывает отсечённое.
- NVIDIA trial «evaluation only»: ограничения RR на синтетические данные остаются как есть.

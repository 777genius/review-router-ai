## 1. Результат и границы

Отдельный компактный verifier проверяет старые unresolved ReviewRouter findings на текущем immutable head. Он независим от OCR/Codex discovery, не ищет новые ошибки, не использует tools и возвращает только `resolved | still_valid | uncertain`. Native GitHub resolve выполняет существующая canonical publication после прежних freshness/authority guards.

В scope: target-driven inventory вне текущего diff; bounded source packets; admitted companion inference; target/participant accounting; exact-head evidence; honest summary и reuse; защита от повторного закрытия после известного предыдущего resolve; contract/recovery/E2E проверки.

Вне scope: agent/retrieval loop, shell/test execution по просьбе модели, второй execution/queue/webhook-controller, новые model/account selectors, вторая mutation authority, cross-head verdict cache, multi-verifier quorum, GitLab lifecycle, redesign discovery или UI настройки агентов. Существующие `off/report/resolve`, confidence thresholds и fail-on-severity сохраняются. Старое допущение architecture/40 «только normal provider prompt, без extra inference» для нового companion заменяется этим контрактом.

Первый вертикальный срез поддерживает **Account Gateway parent Responses transport с OCR или Codex discovery**. Domain/use case не зависит от этих engines. Активация direct OpenRouter provider-API companion отложена: фактический route минует RR relay и не имеет server finite-grant ledger; существующая description-only реализация не доказывает durable spend enforcement для verifier. Codex Secrets/Hosted/остальные неподдерживаемые routes также не получают SDK/API-key fallback. Прежний runtime совместим, новая capability на этих routes unavailable. Это явное ограничение первого среза, а не утверждение об одинаковой авторизации transports.

## 3. Архитектура и ответственность

В A добавить feature `src/finding-revalidation/{domain,application,infrastructure}` в существующем функциональном стиле. Domain владеет tri-state semantics, target identity, packet limits, output validation и eligibility. Application координирует consumer-owned ports `ImmutableSourceReader`, `LifecycleInference`, `PriorResolutionHistory`; adapters читают Git/используют нынешний parent transport. Composition находится в production T0 runner. Domain не импортирует OCR, CodexProvider, Octokit или HTTP SDK.

Verifier получает **один** авторизованный vote identity выбранной connection. Work slot `providerKind` сохраняет выбранную engine authority lane, как существующий companion; `providerCapabilityHash` и отдельная immutable capability прямо указывают executor `rr_bounded_lifecycle_verifier.v1`. Это не OCR output и не второй Codex engine. Повторный call/другой batch той же identity не второй голос.

Краткий consumer contract, точные wire names закрепить в shared contract:

```ts
type VerifyPacket = Readonly<{
  version: 1;
  scope: ScopeAndExactRevision;
  participant: {
    voteIdentityHash: string;
    capabilityDigest: string;
    model: string;
  };
  targets: readonly TargetWitness[];
  sources: readonly ImmutableSource[];
  policyDigest: string;
  packetHash: string;
}>;
type LifecycleInference = {
  infer(
    prepared: PreparedPacket,
    lease: ExistingInvocationLease,
    signal: AbortSignal,
  ): Promise<{
    body: Uint8Array;
    actualModel: string;
    requestHash: string;
    nativeUsage: Usage;
  }>;
};
```

`ScopeAndExactRevision` = workspace/repositoryConnection/SCM repository/PR/base/mergeBase/head/reviewRevisionHash. `TargetWitness` = targetId, threadId, trusted fingerprint, parent ID/createdAt/bodyHash, claimHash, parent updatedAt, full comment-state hash, ledger watermark, original/current path+line, severity, scoped resolution-history fact/cut. Hashes используют existing canonical JSON + domain-separated SHA256; raw claim/thread text — untrusted data, не инструкции. В `review-thread-inventory.ts` transient target дополняется parentCreatedAt/bodyHash до strip/mapping; `github-review-state-adapter.ts` переносит ID/createdAt/hashes к verifier/projection. Raw parent body не сохраняется в server assignment JSON; model видит только отдельно прошедший sensitive check clean claim.

`ImmutableSource` = headSha, exact normalized repository path, Git blob OID, UTF-8 content hash, full file bytes/line count, completeness and inclusion reason. Packet hash покрывает canonical exact target witnesses, sources, prompt/output/policy versions, model/capability и omissions. В model request передаётся этот packetHash; execution/slot/lease IDs привязываются manifest/receipt, не доверяются ответу модели.

## 5. Inventory, immutable context и bounded batching

Стартовать от свежего GraphQL inventory всех старых unresolved targets в PR, не от discovery changed files. Использовать existing pagination/trusted marker/author/ledger rules. Resolved threads исключаются из work. Incomplete inventory делает verification unavailable и запрещает resolve; partial список нельзя назвать полным.

Для каждого target явно сохранить disposition: eligible, human/command/manual, unsupported source, capped, unavailable. Human replies, parent edits/marker ambiguity, untrusted provenance и command dismiss не отправляются модели. Full inventory учитывается в summary даже если большинство targets не поместилось.

Контекст читается из Git objects **exact head**, без mutable worktree bytes: reuse canonical Git inventory/UTF-8 helpers и bounded Git blob reader; не создавать Context Gateway session. Path policy использует выделенный без изменения семантики predicate `sensitivePath` из `pr-description-generation.ts:226-238`, включая .env/secrets/credentials/private-key paths и traversal; дополнительно existing repository exclusions. Symlink/submodule/binary/non-UTF8 unsupported. Старый comment не разрешает запрещённый путь.

В этом срезе source selection **target-file-only**: полный существующий currentPath, иначе originalPath, из native GitHub thread/parent path. Existing LifecycleTarget/PriorLineageHint не содержат authenticated historical evidence[]; отсутствие такого массива нормально. Markdown path mentions не превращаются в дополнительные разрешённые файлы. Shared target files дедуплицируются. Cross-file claim получает uncertain, если packet не доказывает устранение; не создавать artifact lookup service, repo-wide поиск/import scan или дополнительные чтения после ответа.

Применять content detector как `redactSensitiveText(value) !== value` из `utils/redaction.ts:1-29` ко **всему** raw full file и clean title/message/hunk перед отправкой. Если любое необходимое поле требует redaction — весь target `sensitive_context_unavailable`, без model call и без raw content в logs/metadata. Не посылать отредактированный текст с raw Git hash и не придумывать line mapping. Для отправленного source bytes остаются literal Git UTF-8, blob OID+content hash+lines совпадают с citation input. Detector наследует ограниченный набор известных patterns; гарантии нахождения любых секретов нет. Redacted diagnostic reason не содержит сработавшую строку.

Rename поддерживается только когда native currentPath уже указывает на существующий exact-head blob, либо existing current PR file metadata содержит однозначную пару previousFilename→filename для originalPath. Общего historical rename resolver в inventory нет. Если старый rename вне diff не имеет такого mapping — `context_insufficient`, а не guessed path. Missing/ambiguous/deleted path и недоказанный replacement также unverified; deletion не resolved. Старые line numbers — hint, текущие citations проверяются по packet.

Жёсткие v1 ceilings: 4 targets/packet; 2 packets/execution; 6 unique files/packet; 24 KiB/full file; 64 KiB source bytes/packet; 96 KiB полного serialized request; 4 KiB полного claim/target; 32 KiB response; 4 096 output tokens/call; 60s/call; 1 attempt. Использовать меньший из этих limits и captured transport/model limits. Не обрезать claim/file и затем считать context complete: не помещающийся target остаётся unverified. Byte limit не объявлять измеренным token limit.

Порядок candidates: severity descending, затем oldest parent timestamp, затем targetId; packing группирует общие source paths, tie-breaking stable. Сначала discovery планируется с прежним priority/slots; лишь оставшиеся maxWorkSlots отдаются максимум двум verifier packets. Нет места — explicit capped, без вытеснения discovery. Target может принадлежать только одному verifier packet; одинаковые fingerprints разных threadId остаются отдельными targets.

## 6. Расписание, finite allowance и стоимость

Выбор: **discovery → verifier → optional description → projection/publication**. Discovery не ждёт verifier до своего inference; current findings остаются deterministic veto. Дополнительная latency verifier ограничена 120s и не отнимается от времени уже выполненного discovery. Existing execution deadline/publication reserve всё равно имеют приоритет: недостающий remaining time => `verification_deadline`, без нового продления admission.

Gateway сохраняет **весь прежний aggregate native grant `gateway.limits.requests=R` для discovery**: нет hard D/V/P partitions, увеличения R или новой budget policy. Verifier запускается только после терминального discovery inference и может потратить максимум 2 **оставшихся** aggregate requests; description последняя. Если discovery израсходовал R, existing Gateway/native request admission возвращает positively not_dispatched admission_limited: companion `budget_unavailable`, без обхода/пополнения. Это честная bounded availability, не гарантия двух вызовов после любого review. Shadow/local remaining estimate не является spend authority.

Existing relay raw Responses не принимает role/slot/lease identity. Добавить к **этому же relay** узкий companion dispatch admission до SDK/native forward и readback; engine route с прежним aggregate accounting не переделывать. Это одна небольшая таблица/transaction в текущей API/DB, без budget service/queue.

`ReviewRunCompanionDispatchV1`: primary `(authorizationId, dispatchId)`, role `lifecycle_verification|pr_description`, executionId/workSlotId/attemptOrdinal, leaseId/fencingToken, preparedManifestKey, envelopeSha256, stable nativeRequestRef, state `dispatch_may_have_started|not_dispatched|completed|effect_unknown`, safe native usage/result hash, timestamps/retainUntil; unique `(authorizationId,workSlotId,attemptOrdinal)`. Никаких raw prompts/ответов. Retain до исходного auth deadline+existing reconciliation/lease retention; renewal/restore не меняет authorizationId и не обнуляет claims. Discovery requests продолжают учитываться существующим aggregate native grant, не этой таблицей.

Trusted parent добавляет bounded dispatch headers: dispatchId, execution/slot, current lease capability/fence, preparedManifestKey; role сервер **выводит из taskKind stored slot**, не caller role string. Existing lease содержит preparedManifestCanonicalJson/key (`schema.prisma:1705-1745`): exact request body SHA совпадает с manifest providerRequestEnvelopeHash и captured capability/model/schema; lease active/current execution/head/fence. Engine child видит только local loopback token, не companion authority/headers. Unqualified raw traffic не companion evidence и не иной model/capability.

**Submitted/forwarded bytes:** factory сразу создаёт fully normalized bounded Responses envelope: explicit saved model/stream=true/store=false/service_tier=default, без reasoning:null; output cap = `min(4096, captured gateway.limits.tokens, qualified saved-model output cap)`. Последний scalar берётся из уже квалифицированной relay profile/model policy и фиксируется capability, не из нового model registry. До plan target count ≤min(4,floor(outputCap/1024)); cap<1024 => unavailable. Server сначала применяет существующую pure normalization/bounds, затем требует **byte equality** normalized bytes и submitted bytes до claim/forward. Любое silent clamp/remove/reserialize отличие = envelope_not_normalized и 0 SDK calls. После equality один SHA envelopeSha256/providerRequestEnvelopeHash означает обе последовательности bytes. Версию/digest request canonicalizer закрепить shared companion descriptor; не заменять hash после normalization.

Под row lock существующей ReviewRunAuthorization: перепроверить authority/deadline/lease и stored slot; same-ID identity/body hash; count lifecycle companion claims ≤2 и description ≤1; insert dispatch_may_have_started со stable nativeRequestRef. Только владелец нового insert может вызвать SDK; V+1/description+1 отвергаются **до SDK forward**. Затем существующий aggregate native admission отдельно обеспечивает R+1 not_dispatched, включая прямой вызов relay без local counter. Start/lease/observation validators связывают claim с accepted observation; post-inference validation не заменяет pre-dispatch claim.

**Exactly-one scoped forward:** новая companion ветка relay расположена **вне** существующего discovery `for(;;)` wait/retry loop (`review-run-gateway-relay.ts:495-528,640-708`). Owner нового claim вызывает ровно один `session.preparation.request(storedNativeRequestRef, exactBytes, ...)`; не генерирует новый rr-request ref, не ждёт admission_limited для повторной попытки. Public companion HTTP transport также one-shot, без автоматического client retry/redirect replay. Discovery loop остаётся прежним. Existing SDK request invocation/transport qualification должен подтвердить отсутствие скрытого второго dispatch для этой ветки.

Повтор dispatchId+facts даёт только bounded readback status/ref/hash, **не SDK call**; другой body/facts — conflict. Другой ID того же slot/attempt — already claimed. Crash после claim, даже до forward, консервативно расходует companion one-attempt budget; native grant расходуется по своему protocol. Definitive unpaid denial допускает not_dispatched/budget_unavailable лишь при explicit native no-dispatch proof этого stored ref, но reservation не recredit и retry нет. Completed без accepted observation не разрешает повтор inference. Existing native status/same-operation recovery используются, не обходятся.

Settlement transition monotonic: после начала SDK call status остаётся dispatch_may_have_started/effect_unknown, пока explicit native proof не докажет completed либо not_dispatched. Callback/usage/DB/stream/HTTP ошибки **не** proof unpaid; они не возвращают управление в retry loop, не обнуляют claim и не переводят may-have-started в unpaid. Если settlement DB write не прошёл, durable исходный claim остаётся may-have-started; readback/reconciliation с тем же nativeRef, 0 replay. Native no-dispatch proof, не сохранённый из-за DB failure, тоже не создаёт fresh allowance.

Restore читает claims того же authorizationId под lock; process-local counters только preflight. Description в новом enabled profile тоже использует scoped claim; legacy profiles продолжают старый route без новых прав. Последовательность закреплена orchestrator: discovery slots завершаются до companion, optional failure не останавливает discovery, поздний verifier не запускается параллельно с engine. Если discovery не терминален, companion dispatch отклоняется как phase_not_ready. Конкретная availability измеряется по fixtures; при частом исчерпании R feature честно abstains, профиль самостоятельно не расширяется.

Direct OpenRouter provider-API forwarding (`account-gateway-model-transport.ts:775-813,1036-1057`) минует RR server: provider quota/rate limit не реализуют V≤2 или restore fence. Поэтому этот route **deferred/unavailable для новой verifier capability**, existing discovery/description без расширения scope остаются прежними. Будущая активация потребует отдельного explicit transport qualification, не простой замены URL. Не создавать API credential/model fallback сейчас.

`limits.tokens` relay применяет к max_output_tokens; не называть его автоматически общим input+output budget. Каждый verifier request использует `min(4096, captured gateway.limits.tokens, qualified saved-model output cap)`; если output cap не покрывает выбранный packet, уменьшить target count до приготовления plan, иначе skip. Не менять модель из-за её context limit: provider rejection оставляет unverified.

Usage: отдельные native per-call request/attempt IDs и role `lifecycle_verification`, источник существующий Responses usage observer/delivery. input/output totals inclusive; cached/reasoning — subdivisions, не прибавлять повторно. Missing native usage = unknown, estimator characters/token — отдельно помеченная estimate. Ноль eligible targets => ноль model calls. USD обещаний без tariff/actual usage нет.

## 7. Ответ, evidence validation и policy

Output strict JSON: `{version:1, packetHash, results:[{targetId, fingerprint, verdict, confidence, scopeSufficient, failureCondition, fixExplanation, evidence:[{path,blobOid,startLine,endLine,quote,reason}]}]}`. Unknown keys/types, unknown/duplicate targetIds, wrong packetHash/fingerprint, invalid UTF-8/oversized/malformed/truncated envelope отвергают весь packet. Missing target не скрывается: packet остаётся без accepted verdicts, все assigned targets unverified `missing_or_invalid_verdict`. Не делать model retry ради исправления JSON.

Каждый citation указывает current-head source из packet; blobOid совпадает, line range целочисленный и внутри полного файла, quote непустой и буквально присутствует в указанном range. Old diff hunk/PR description/другой head не current evidence. Проверять до нормализации в existing lifecycle payload; manifest сохраняет immutable source/target hashes. Zero findings, bounded rationale/evidence, actualModel совпадает с captured selected model, receipt requestHash совпадает с prepared request bytes.

`resolved` требует scopeSufficient=true, хотя бы одного валидного current citation, непустого объяснения исходного failure condition и конкретного механизма его устранения, existing confidence ≥ critical .90 / major .85 / minor .80 / unknown .90. Model confidence не calibrated probability; наличие citation доказывает соответствие packet, не семантическую истинность. Если модель сама указывает требуемые, но отсутствующие callers/config/dependencies — uncertain. Fixed packet сознательно чаще abstains на непрямых ошибках.

`still_valid` требует валидного current evidence и причинного объяснения; он и matching current finding veto resolved. Отсутствие finding, green CI, changed/deleted/unchanged file не доказательство. `uncertain` не требует выдуманной citation, включает причину недостаточности.

**Raw veto boundary:** `ProductionReviewProjectionCommandFactory` сохраняет normalized findings из всех accepted **discovery** observations до synthesis/presentation selection в `command.currentFindings`. В `BuildCurrentReviewProjection.execute` после fresh inventory, но **до selectCurrent**, existing legacy matching adapter вычисляет `recurrenceVetoTargetIds` из этих raw candidates; передать explicit facts в ProjectLifecycleQuery и применить до принятия resolved. Использовать существующий `currentFindingMatchesTarget`/`isLikelySameInlineFinding` (`thread-lifecycle.ts:536-552`, `comment-fingerprint.ts:153-196`) с теми же переводами candidate/target, а не правило «тот же file/function». Не менять global matching heuristics. Наличие veto не публикует скрытый discovery finding заново, но запрещает resolve и All Clear для этого target. Unrelated new minor в той же функции остаётся новым finding и не veto исправленные старые failure modes.

Planned verifier roster для нового среза содержит ровно одну identity; per-target assigned/missing/exhausted/capped состояния берутся из lifecyclePlan. Discovery lanes не являются lifecycle participants. Accepted responses никогда не определяют roster. Missing единственного verifier = no quorum; два batch ответа той же identity = один vote. Explicit multi-roster decoder/validation не должен при потере responder сжимать quorum; multi-verifier scheduling вне scope.

Перед projectLifecycle сопоставить accepted verdict с fresh target witness: repo/PR/head/targetId/threadId/fingerprint/claim+parent version/comment hash/ledger и **captured prior-history cut** совпадают. Foreign history changes после cut проверяются отдельно (§8); own canonical progress не инвалидирует packet. Stale binding => discarded/unverified, fresh inventory не «освежает» ответ автоматически. Exact-head source cache допустим; cross-head verdict reuse запрещён независимо от file hash. Existing T0 reuse требует exact revision/plan/model/policy/packet+target/live hashes; changed plan/roster invalidate reuse.

Coverage разделить: discovery file completeness как прежде; lifecycle verified/skipped/unverified отдельно. Optional verifier failure не превращает discovery в failed/partial file coverage. **Любая partial discovery запрещает все lifecycle mutations**, даже при semantic resolved. Uncertainty не severity failure, но блокирует All Clear.

**Explicit confirmation representation:** добавить narrow `LifecycleVerificationFact` в projection lifecycle row и application queries: `{targetId, lineageId?, semanticVerdict, confirmationState, severity, observationIds, providerVoteKeys, reasonCodes, mutationStatus}`. Эти факты выводятся только из accepted scoped observations и fresh bindings; входят в canonical projection hash/new producer render policy и shared validator. Старые envelopes без extension читаются как прежде. Не полагаться на current `priorOccurrenceState` (StillValid/Resolved оба CarriedUnverified) или legacy report_mode→Uncertain mapping.

| Вход нового companion                                                                            | confirmationState / summary                                                | Merge gate / mutation                                                                                                 |
| ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| valid still_valid                                                                                | confirmed_open, прежние target/lineage/severity и verifier provenance      | учитывается failOnSeverity даже вне diff; resolve veto; summary-only, без нового inline/unresolve                     |
| valid resolved, report                                                                           | fix_confirmed_thread_open, mutationStatus=report_only **as of projection** | нейтральное «исправление проверено»; native Resolved/closed lineage не выводится                                      |

| valid resolved + partial discovery                                                               | fix_confirmed_thread_open, blocked_partial_review **as of projection**     | 0 mutations; partial/inconclusive gate сохраняется                                                                    |

`ProjectReviewPresentationQuery` и `EvaluateMergeGateQuery` явно получают эти confirmation facts. **Identity без baseline допустима:** confirmation всегда имеет native targetId/threadId/fingerprint; lineageId указан только при реальном prior hint/существующем occurrence, synthetic occurrence/lineage запрещён. При known lineage existing blockingLineageIds ссылаются только на настоящие occurrences; narrow extension отдельно несёт `blockingConfirmedLifecycleTargetIds` + reason/provenance и валидирует их по confirmed_open facts. Gate=Fail при непустом любом blocking set, даже когда occurrences/lineageIds пусты. `validateMergeGateDecision`/`applyBlockingDecision` сохраняют старый occurrence invariant и отдельно проверяют/применяют target blocking facts.

Authoritative `deriveReviewPresentation` складывает confirmations **до canonical counts**: target с matching current occurrence учитывается один раз как current; target с known carried lineage заменяет её unverified contribution на confirmed_open, а не добавляется поверх; target без occurrence учитывается один раз по targetId в confirmed_open. Дубли confirmation того же targetId не допускаются; отдельные native targets остаются отдельными до existing matching/lineage relation, нового semantic dedupe не изобретать. Severity берётся из fresh trusted target и accepted confirmation. No-baseline case не требует поддельного finding/inline, missing baseline не inventory failure. Report positive fix сохраняет semantic confirmation и не report_mode→Uncertain. Current/confirmed-open, fixes-verified и unverified counters раздельны; native-closed count current artifact не увеличивается от его pre-effect candidates.

## 8. GitHub effects, ручные действия и recovery

`resolved` model verdict — semantic candidate. **Current immutable summary/check говорят «N исправлений проверено» / «N fixes verified»**, а closure status обозначен **на момент projection**, например «закрытие запланировано» или «report-only, без автоматического закрытия». Внутреннее имя fix_confirmed_thread_open обозначает наблюдение в этот момент, не бессрочное present-tense утверждение UI «thread открыт». Из candidates нельзя вывести «N threads resolved» текущей publication. Fallback-комментарий «resolved» также не native closure proof.

Existing native lifecycle operations и canonical receipts/effects немедленно записывают фактический success/denied/unknown исход, который доступен operation outcome readback. Они **не переписывают** finalized projection/artifact, operation catalog/markerHash/bodyHash или snapshot: даже snapshot commit после successful publication использует исходный artifact. Current snapshot остаётся честным verification-time снимком. Лишь **следующая обычная projection**, получив fresh native closed state и соответствующее confirmed effect evidence, может показать native_resolved/closed lineage/count. Срез не добавляет второй render/publication job, queue или автоматический новый model run; немедленный aggregate «N threads resolved» update вне scope.

Переиспользовать current publication permits/generation fences, head guard, thread comment-state witness, ledger watermark и App-first authority. Fresh final guards проверяют trusted unchanged parent/body/fingerprint, complete pagination, no human discussion/commands, current unresolved thread/repo/PR и permission. Новая feature формирует только resolve operations; still_valid не становится unresolve/reopen. Совместимость старого renderer с historical Reopen operations сохраняется вне нового capability.

**History guarantee ограничена доказуемой границей, не lifetime absence.** Existing DB имеет retained operations/effects, но не trustworthy purge lower watermark; empty query не доказывает отсутствие старого resolve. Нынешний appliedComparisonResolutions также требует whole-attempt success. Не ставить все существующие targets в вечный unknown лишь потому, что такой lifetime census никогда не существовал.

Для известного RR reopen guard добавить минимальные durable facts в существующий publication repository: per-repository immutable `resolutionGuardActivatedAt` и per-thread compact `ReviewThreadResolutionGuardV1` keyed workspace/repository/PR/thread, с first known confirmed resolve operation/effect ID+publication/execution/generation, pending/unknown canonical resolve ID, monotonically increasing guard version. Записывать pending guard в той же DB transaction, которая выдаёт canonical resolve operation capability **до эффекта**; confirm/known-no-effect обновлять при existing effect/receipt transaction. Compact positive/pending guard не удаляется вместе с подробными retained receipts; срок жизни — до удаления repository connection/PR data по действующей policy, не новая история всех событий.

**Activation entry contract новый и connection-scoped, не уже существующий сильный fence.** На repository connection хранить `lifecycleEntryMode=legacy_open|draining|guarded` и activation/version fields. Legacy resolver при входе, **до async token/head/thread reads**, под row lock connection проверяет legacy_open и записывает pending legacy entry ID+точный target/thread в том же compact resolution guard (sourceKind=legacy_entry). Для одного thread не допускать второй unresolved legacy entry. Перед mutation пометить may_have_started, terminal no-effect/confirmed/unknown settle туда же; unknown не истекает в разрешение. Canonical capability issuance пользуется тем же gate transaction и пишет pending canonical operation до эффекта. Это несколько policy fields/transactions существующих repositories, не maintenance framework/новый controller.

Cutover: атомарно mode=draining запрещает **новые** legacy entries и новые неучтённые canonical capabilities; existing entered requests либо уже terminal, либо имеют durable pending exact-thread guard. Уже выданные canonical capabilities включаются в pending backfill, даже без receipt. Retained confirmed/pending effects backfill независимо от whole-attempt outcome. После проверки всех accounted writers фиксировать activation cut/writer digest и mode=guarded; legacy route тогда guarded_publication_required. Pending accounted old request может завершиться после cut: его target уже защищён pending guard и последующий effect settle не потеряется.

**Uninstrumented old process не считается drained по нулевому счётчику/пассивному Gate0 read.** Для первого включения нужна проверяемая quiescence прежних managed writers: actual deployment executors старого binary больше не принимают вызовы и все уже-entered handler/effect promises завершены с terminal outcome либо их exact targets внесены как durable unknown pending. Graceful drain должен ждать effect handler settlement, а не только закрытия клиентского HTTP socket; время ожидания само по себе не proof. Если actual rollout adapter не может подтвердить это после старого crash/неучтённой mutation, connection остаётся draining/unqualified, resolve capability unavailable; discovery/report доступны. Не выдумывать такого pre-existing сильного fence по source. Будущие rollout после установки entry instrumentation используют durable gate/entries без нового generic framework.

Qualified canonical writer пишет guard независимо от возраста producer. Unmanaged standalone Action/GitHub user writes остаются внешними необозримыми действиями: cut не гарантия их учёта. Это ограничение authority scope отдельно от учтённых legacy backend requests, которые должны удовлетворить predicate выше.

Readback на existing comparison-baseline companion возвращает parentCreatedAt, activation cut, target-specific guard version/facts и captured historyCut. Для parentCreatedAt≥activationCut и работающего qualified writer policy отсутствие positive/pending guard означает **no_prior_rr_resolution from creation through cut**. Для более старого parent: `no_known_resolution_since_cut` плюс `legacy_history_before_cut_unobserved`; это **не lifetime proof и не автоматический veto**. Legacy targets продолжают полезно проверяться/закрываться один раз при остальных guards. Известный retained prior confirmed resolve блокирует независимо от возраста; unknown фактически dispatched historical resolve блокирует до reconciliation. Невосстановимая legacy history может скрыть pre-cut manual reopen — явный residual risk первого rollout, а не ложный no_prior. Внешние resolve→reopen cycles без RR effect тоже не полностью наблюдаемы. Такой scoped guard сохраняет действующие human-reply/known-reopen protections без вымышленной полной истории.

Если сейчас unresolved и **foreign/prior** confirmed RR resolve известен — manual attention `previously_resolved_thread_reopened`, без автоматического reclose. Реальный unresolved-unknown effect — `resolution_effect_unknown`, без новой inference/mutation. Возобновление требует нового finding/thread или существующего явного user action; reset UI/command не создавать.

**Own-operation exclusion:** history cut фиксируется перед текущим publication; сравнивать captured prior facts плюс новые **foreign** facts после cut, не глобальное равенство watermark. Собственный progress допускается только когда guard operation/effect принадлежит этому canonical publicationAttemptId/execution/generation, target thread, exact head и planned resolve operation/bodyHash. Он считается expected progress: current resolved reconciles as applied/already-applied; lost ACK использует тот же operation/effect readback, не новый resolve. Собственный pending/confirmed guard не делает остальные targets stale и не превращается в manual reopen. Если после собственного confirmed effect thread снова unresolved — не повторять resolve: это reopen/changed state и manual attention. Foreign generation resolve→unresolved блокирует даже при unchanged comment hash.

Revalidate freshness/target-specific guard снова на publication boundary под existing generation fences. Два кандидата одной publication могут закрыться последовательно. Другой run уже закрыл thread — current native readback external/already-resolved, без повторной модели. Смена head отменяет affected work; stale evidence не attach/reuse для нового head.

**Restore priority, включая полный public process restart:** сразу после authorization/exact-revision check production runner читает существующий execution restore **до нового планирования**. Narrow existing restore response/readback возвращает persisted planHash/assignment JSON/slots и, если она уже создана, publicationAttemptId+artifact/projection identity/source revision. При current own publication сначала восстановить именно эти plan/selected witnesses/artifact и вызвать существующее publication reconciliation/status; не build нового plan/start identity, не reselect targets, не evidence lookup/inference replay из-за смены aggregate inventory hash. Closed A из собственного resolve закономерно исчезает из unresolved inventory: это expected own progress, а не основание выбросить accepted packet с нетронутым B.

Publication recovery проверяет remaining target witnesses **индивидуально** свежими guards. Только exact own-operation allowance выше допускает исчезновение A/его native closed state; B должен сохранить свой claim/parent/comments/head/ledger. Foreign изменения invalidируют affected remaining target/operation, не открывают бюджет для replan. Reconcile lost ACK A по тому же operation/native effect, затем продолжить safe B в прежней publication. Если публикация ещё не начата, restore всё равно использует stored execution plan и accepted evidence; changed foreign inventory не обновляет старые target bindings и не разрешает повтор inference. Лишь новый явно независимый execution с обычным новым admission строит новый inventory digest/plan. Cross-head reuse запрещён во всех ветках.

После timeout/transport failure/cancellation paid inference effect неизвестен: сохранить failure/effect identity, исчерпать one-attempt slot, не запрашивать новый call. Restore принимает только already accepted exact evidence; uncertain unaccepted dispatch остаётся unverified. Positively unpaid pre-dispatch denial тоже не запускает автоматический второй model attempt в этом срезе.

Unknown GitHub mutation outcome reconciles через existing canonical operation lookup/native state и effect receipt, без слепого нового resolve. Permission denied/rate-limit/head/thread change сохраняют thread открытым и отдельный mutationSkipped/Failed/Unknown status. Известный failed write не превращает semantic candidate в fixed/native closed lineage.

GitHub ResolveReviewThreadInput не имеет expected-head/thread-version CAS. Final-read→write human/push race полностью не устраняется клиентом; guards и reconciliation ограничивают риск, но абсолютную гарантию не обещать. Официальная схема уже проверена исследованием: https://docs.github.com/en/graphql/reference/pulls#resolvereviewthreadinput .

## 10. Acceptance и проверки при будущей реализации

Каждая новая проверка должна ловить конкретный observable defect; не требовать количества unit tests/LOC. Использовать существующие fixtures/suites и meaningful contract/Postgres/paired tests там, где mocks не доказывают authority/recovery.

- Four-target fixture в явных 24 KiB file/4 KiB claim bounds: два старых tax failure modes исправлены; один сохраняется, один требует отсутствующей cross-file зависимости. Ожидание — 2 semantic candidates, 1 still_valid, 1 uncertain. Добавить unrelated new negative-rounding minor в той же функции: это отдельный current finding, не veto двух исправлений. Отдельный matching raw recurrence, скрытый selectCurrent/presentation, всё равно veto. Только первые два candidates native-resolvable при полном discovery/guards; вне-diff target проверяется, resolved/human-discussed не model work.
- Response/citation faults: duplicate/missing/unknown IDs, wrong packet/model/hash, invalid JSON, fabricated path/blob/quote/range, zero evidence, insufficient scope и model truncation не создают accepted resolved. Не ловить только mock вызов/parser source text.

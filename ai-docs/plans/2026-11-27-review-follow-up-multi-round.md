# Review failures: additional cross-execution investigation

Read-only multi-round follow-up through 13:13 UTC on 27 November 2026. This supplements `2026-11-27-production-review-failure-investigation.md`; it does not establish that every failed run has been classified, that failures share a root cause, or that any production behavior has been changed.

## Retry advice and uncertain prior effects

[Run 45946440787](https://github.com/agent-teams-ai/.github/actions/runs/45946440787) logged GitHub 403 rate limiting, `revision_guard_unavailable`, a model request with `effect_unknown`, and close `unknown`. Its pinned `workflow-v1` Action source was `e0e5f8fac3985560ba4848d084258d3623cbc4f2`. In `src/review-execution/domain/provider-failure.ts` around lines 69–91 that version appends the advice to wait for the run and start a new review to the broad upstream/request-outcome failure class, without checking Gateway physical-close evidence. The existing `lifecycle-verification-transport.test.ts` case around lines 373–410 checks one transport and the message, not a second independent execution.

Two separate source inspections found that deployed ReviewRouter `6271ebe1` treats a manual rerun as a distinct request and, on admission, supersedes the prior execution and revokes its logical leases (`review-requested-intent.ts` 485–502, `review-v2-request-ingress-handler.ts` 140–168, `review-execution-preparation-transitions.ts` 245–305). Logical revocation alone is not evidence that a forwarded provider request or its transport has physically ended. The allocation deletion guard in migration `000152_review_run_gateway_allocations` preserves uncleared old custody but does not by itself prohibit a new authorization.

For Gateway `a3dafad`, occupied transport accounting in `services/account-gateway/src/postgres.ts` 1427–1442 is scoped to `(consumer, execution_ref)`; duplicate reservation nonce checks at 1448–1461 are not a cross-execution guard. The check for all open executions at 433–463 is part of reconnecting a disabled account, not general model-request admission. These observations do not prove that a second request was dispatched, that effects overlapped, or that duplicate charges occurred in this particular run. They show why the existing evidence cannot promise that starting a new execution after the GitHub job ends is free of overlap or cost while the old effect and close remain unknown.

Investigate the exact old execution and request with authenticated readback and sanitized identifiers, and validate the current product's retry advice and admission end to end. Test two independent executions, unknown prior effect/close, late provider completion, old-lease revocation, revision change, new admission, custody and physical-transport readback. Distinguish a safe refusal, bounded waiting and separately authorized user retry from automatic replay. Do not automatically replay the same unknown-effect dispatch or assume lease expiry proves provider cancellation.

## Capacity pressure and closure retries

The relay close timer has a bounded retry loop: one initial close plus eight retries, and a separate deadline timer can issue an additional close. Existing `review-run-gateway-byte-limits.test.ts` cases around 3302–3351 check that sequence, stable operation ID/reason and no repeated inference; cases around 3418 cover shutdown timers. `review-run-gateway-relay.ts` around 1090–1103 releases local session custody only on applied close or proved empty custody, while pressure admission around 772–779 attempts reclaim before checking the session cap.

An unconfirmed close that remains retained and is still unconfirmed during pressure reclaim can contribute to saturation; this is a code-path hypothesis, not attribution of the historical 16-slot incident to exhausted timers. Add an isolated fake-clock, `maxSessions=1` test: unknown close through the existing timer budget, pressure from a distinct request, asserted reclaim and admission outcome, then an applied close before expiry and verified release/new admission. Assert the same close operation ID and no repeated model inference. Separately test expired capability as a refusal with custody retained, without inventing an after-expiry proof. The previously rejected after-expiry proof must not be reused or bypassed. A missing log does not establish physical transport closure or free occupancy.

## Cross-repository status mismatch and positive controls

Two additional historical `workflow_dispatch` runs, [get-modular 45730346863](https://github.com/agent-teams-ai/get-modular/actions/runs/45730346863) and [agent-teams-platform 45721224252](https://github.com/agent-teams-ai/agent-teams-platform/actions/runs/45721224252), returned GitHub success while their corresponding ReviewRouter executions later became `failed` near deadline. Both recorded OCR SIGKILL followed by AbortError, `transport/effect_unknown` and unknown close; no finalized projection artifacts or publication attempts were found in the inspected V2 tables. The pinned Action can send SIGKILL on an abort signal; the logs do not establish that signal's source or establish that the green conclusion was wrong. No newer executions for those same PRs were found in the following six hours in the inspected data. Zero rows in these V2 tables do not rule out every possible GitHub comment.

Positive controls after deployment: [45993115256](https://github.com/777genius/review-router-ai/actions/runs/45993115256) and [46000294076](https://github.com/agent-teams-ai/.github/actions/runs/46000294076) had database `completed`, GitHub success, App publication completed, Gateway request readback completed and close applied around 12:54–12:56 UTC. These two successes do not establish reliability across all failure modes. As of the 13:13 UTC read-only snapshot, no new terminal `partial` or `failed` execution had been observed after 12:40; data may change and this is not a prospective guarantee.

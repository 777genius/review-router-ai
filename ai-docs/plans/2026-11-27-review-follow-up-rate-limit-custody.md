# Review follow-up: Action rate-limit bounds and cross-execution custody

Read-only follow-up through 13:32 UTC on 27 November 2026. This documents source behavior and bounded observations, not a production fix or a complete census of review failures. The other investigation documents and current PR implementation remain independently owned.

## Confirmed Action retry-boundary defect

The public Action's `src/github/client.ts` at `5e07138c` and the `workflow-v1` commit `e0e5f8fa` used by [run 45946440787](https://github.com/agent-teams-ai/.github/actions/runs/45946440787) have identical logic for this path. `rateLimitWaitMs` returns a valid `Retry-After` immediately and only consults `X-RateLimit-Reset` when that header is absent or unusable. Consequently, a response with `Retry-After: 1`, `X-RateLimit-Remaining: 0` and a valid reset 60 seconds in the future can cause an otherwise eligible GitHub read to be retried approximately one second later, before the declared reset. For the conflict use case, the conservative bound is the maximum of the valid Retry-After delay, the valid remaining-zero reset delay and jitter; do not initiate a wait that cannot fit the remaining retry window.

The existing client retries only GET/HEAD/OPTIONS, classifies 429 as rate-limited and 403 as such when `Retry-After` is present or remaining is exactly zero. Its three retry intervals use 1/2/4-second exponential delays with 50–100% jitter, bounded by a 15-second wait window; this is not a wall-clock timeout for an entire request, whose timeout is controlled separately by the caller. There is a separate one-time 401 credential refresh. For a classified rate-limit response without usable rate-limit metadata the fallback delay is 60 seconds. A valid zero delay and an already elapsed reset are distinct from missing or malformed headers.

The saved log for 45946440787 establishes a GitHub 403 and other failures, but does not preserve these response headers. It therefore **does not prove** this bug caused that specific 403 or that an early retry happened there. PR #1028 modifies a ReviewRouter revision adapter; it does not modify this separate public Action client. The Action tests around `__tests__/unit/github/client.test.ts:259–305` exercise Retry-After and reset separately, not the conflicting combination. Add deterministic fake-clock tests for 403 and 429: short Retry-After with reset beyond the remaining 15-second window (no retry), both within the window (wait the later bound), and long Retry-After with earlier reset; include missing/malformed headers, zero, elapsed reset, HTTP-date, budget equality and safe-method gating. Fix and release the Action in its own qualified workstream; do not assert that the ReviewRouter change alone ships this fix.

## Effect state is distinct from transport closure

Gateway `a3dafad`, `services/account-gateway/src/postgres.ts:1521–1574`, retains a confirmed completed effect after worker loss; on message handling or reconciliation after lease loss before confirmed completion it records `effect_unknown` and fences the old execution. The crash alone does not immediately write that state. Reconciliation around 1812–1833 likewise does not make an unknown provider effect known. Exact native closure or cleanup proof is needed to release transport occupancy (1670–1681); cleanup cannot become done while transport remains occupied (2060–2078). Conversely, confirmed transport closure alone does not establish that a provider never processed or billed the earlier request.

ReviewRouter `6271ebe1` distinguishes recovery of the same running execution by authorization ID, mutation epoch and revision (`review-execution-preparation-transitions.ts:210–223`) from admission of a new execution: stale/unavailable admission does not supersede the active one (245–268); a valid new admission can supersede it and revoke logical leases (270–305). These are domain transitions, not evidence of physical transport closure. Gateway request identity `(consumer, execution_ref, request ID)` is idempotent for the same identity (`postgres.ts:1355–1362`); a new execution/request identity is distinct. Although the Gateway scans lost owners by account, `reconcileRequests` around 1834–1836 with a specified execution ref returns true only when a discovered request belongs to that execution; do not infer that an unrelated new execution is automatically blocked by an old execution's ambiguous custody. These source observations do not prove actual overlap or duplicate billing.

In isolated PostgreSQL/Gateway/Action fixtures, separately test same-identity recovery and a new superseding identity, worker crash after send, completion before and after loss, stale or incorrect closure evidence, new admission before/after confirmed close with effect still unknown, and independent PR concurrency. Assert no automatic replay of an unknown-effect request and no false claim of non-entry merely from closed transport. Respect the separate prior automated safety rejection of an after-expiry proof; do not use or bypass it.

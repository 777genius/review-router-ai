# Installed runtime transition: focused review addendum

Status: focused root/recovery review accepted; the bounded server and runner adapters are implemented and have synthetic qualification below. This is not a production observation or rollout qualification.

## Verified current boundaries

- Direct API setup selects `REVIEW_ROUTER_CODEX_ROTATING_ACTION_REF`; Hosted setup selects its paired recorded tag/SHA/dist; Gateway keeps `workflow-v1` while its selected producer uses the rotating primary. Readiness must qualify that exact target, rather than any configured overlap candidate. An already compatible immutable installed caller remains valid during a target change.
- `resolveCodexRotatingProvisioningActionRef` preserves the exact attested active Secrets pin. Release runbook section “For a rotating A -> B release” requires a fenced drain and fresh namespace. The active namespace stores one exact workflow attestation.
- Existing `replaceActiveWorkflowSource` permits V4→V5 with a specific bounded previous-source contract, or the isolated canary workflow. It is not a general V5 A→B upgrade primitive.
- `issueCodexRotatingSetupCommand` already rejects pending/unknown writebacks and a live runtime lease, takes the provider lock, increments its mutation epoch, and enters `setup_pending`. It does not establish a complete GitHub queued-run drain.
- Existing setup claims contain generation/account hashes and byte size, then accept a sealed GitHub PUT and definite outcome. The SaaS never receives auth plaintext. The existing seed installer supports explicit repo-scoped auth, `--skip-login`, and known-current auth reuse; it still needs a local auth source and GitHub public-key access.

## Smallest credential-preserving route

1. Qualify exact B producer/profile, installer digest and provisioning target as one existing release tuple. Keep A trusted for already admitted work. Do not invent a release SHA.
2. Provision a narrow, exact-B `workflow_dispatch` migration caller in the same repository through the existing App-owned setup PR mechanism. It reads only the currently active namespace's GitHub secret. A cannot execute B migration code without installing this bootstrap caller first; a server cannot retrieve the existing secret's plaintext.
3. Stop new old-workflow admissions using observed GitHub workflow disablement, then observe all queued/in-progress runs to terminal outcomes and require the existing provider lease/writeback fence to be clear. Do not cancel admitted work, expire it by assumption, or use an empty local counter as drain evidence. Recheck workflow identity and disabled state immediately before taking the provider mutation fence.
4. Allocate the existing setup manifest under that fence, with an optional, purpose-specific migration binding to original namespace/epoch, exact generation hash/account identity, source A and target B. The existing claim persistence must compare those original facts, so stale runner secret snapshots cannot silently reseed an older generation. This is the minimum extra admission boundary; a client assertion alone is insufficient.
5. Dispatch only a nonauthorizing migration identifier. The exact pinned bootstrap runner exchanges GitHub OIDC for the existing setup capability only after source/workflow/ref/run/namespace/fence verification; do not put a bearer setup nonce in persisted `workflow_dispatch` inputs. The runner reads the exact active secret after issuance, proves its original generation/account using the original provider's hash salts and compaction contract, then separately computes the fresh namespace's seed hash. The existing setup contract currently preserves these provider-level salts across namespaces; both sides explicitly validate that fact. Never compare digests across different salts or trust a client `current` flag. Reuse the existing compaction/hash/sealed PUT pipeline, perform no OAuth refresh or login, and wipe temporary plaintext. The server receives only existing hashes and sealed GitHub ciphertext. No generic secret-copy service or second queue is introduced.
6. Confirm the fresh namespace through existing setup outcome semantics. Unknown PUT never activates or retries the same possibly applied effect; existing ambiguous retirement/recovery rules apply. Keep the old namespace and A immutable until this point.
7. Render and verify the standard B caller against the new namespace through the existing setup PR/activation path, then re-enable its review workflow. The bootstrap migration caller is removed in that setup PR. The current primitives therefore need two reviewable setup revisions (bootstrap, then final caller), not an unsafe rewrite of an active A attestation.

## Decisions settled by narrow review

- Two reviewable setup revisions are accepted. There is no currently installed migration entrypoint to dispatch, and neither PR is automatically merged. The existing Update action first offers the bootstrap PR, then continues the drain/seed after its merge, then offers the final caller PR. The UI preserves the actual old installed state during the first PR.
- Public-key facts come from the existing repository-scoped `OctokitCodexRotatingGitHubSecretGateway` public-key read, delivered by the OIDC-authorized setup response. `github.token` must not be assumed to have secret-read permissions. `OctokitReviewV2DispatchCapabilityInspector` can establish repo-scoped Actions write authority. Never send an App write token or plaintext auth to the runner unnecessarily.
- Complete ingress/queued-run observation and binding into the setup mutation fence are new concrete adapters. No current function proves them. Existing OIDC/workflow source verification must bind the migration caller before it receives the capability; no generic browser-to-runner capability dump.
- Persist migration binding as a narrow optional field in the existing setup manifest/claim contract, preserving older immutable installer behavior and not overloading IDs/statuses. No new attestation-history table, runtime queue, credential store, or publication engine.

## Implemented bounds and evidence

The optional `runtimeMigration` field in the existing immutable setup manifest binds the original provider mutation epoch, active namespace, generation/account proof, source attestation, exact target B, bootstrap source and finite ingress workflow identities. The existing provider row lock protects the final drain recheck and ordinary setup allocation. No Prisma table, credential store, queue, or publication path was added. Ordinary seed installers keep their previous manifest and dispatch behavior.

The GitHub adapter checks the current repository/default branch and exact source bytes before and after complete paginated inventories. Every observed run must be terminal, and ingress must be observed as `disabled_manually`. A missing, changing, truncated, unindexed, unknown-state or oversized inventory fails closed. Reads are bounded to 100 pages of 100 entries and five seconds per HTTP request; a repository exceeding these limits remains unavailable for this automatic transition. These limits do not turn partial observations into a drain proof.

The setup manifest allocation is the durable admission for at most one workflow dispatch. A fresh allocation may dispatch its nonauthorizing migration identifier once; an existing allocation only reads back the exact run. Lost acknowledgement, duplicate matching runs or a crash between allocation and dispatch produce explicit recovery state. No second dispatch is inferred from absence. Disable and final enable also read back exact state after an uncertain acknowledgement. After the ingress fence changes, failure never automatically re-enables A.

The existing GitHub OIDC verifier is reused through a narrow adapter export. Each runner must independently match repository, audience, workflow source, immutable reusable B, branch, run identity and attempt 1 before receiving the setup capability. The server then checks the original namespace, generation/account/hash domain and provider fence again. Claim `operationId` must equal the migration ID, and the one setup dispatch key is deterministically `runtime-migration:<migrationId>`. Neither a second runner nor an explicit new key can allocate a fresh secret PUT. Migration also disables the ordinary installer’s predispatch retry chain. Two simultaneous runners may conservatively fence the first before its PUT; this is an availability limitation, not permission to retry the effect.

A confirmed candidate finishes on the exact B captured in its immutable manifest while B remains in the explicitly trusted release overlap, even if the global primary changes to C. Retirement of B blocks completion. New migration allocation and fresh OIDC exchange continue to require the current qualified primary/installer/producer tuple; release operators must retain that tuple while its short-lived migration admission is outstanding. Final activation verifies the ordinary B caller and new namespace, proves bootstrap removal, and only then re-enables the exact review ingress. An unknown setup outcome is not mistaken for a confirmed candidate.

Synthetic verification uses the actual runner compaction/HMAC/identity/sealed-box code (20 focused cases) and the actual PostgreSQL setup/effect ledger with generated RSA-signed GitHub OIDC (three paired cases: confirmed PUT, uncertain PUT, and concurrent dispatchers). The PostgreSQL cases start through ordinary setup and native activation, enforce all effect guards, preserve one claim/attempt and at most one PUT, reject alternate keys and stale proof, and leave A active until the final verified revision. The confirmed case continues through native B activation and A retirement, denies enabling while the bootstrap still exists, then reconciles a lost enable acknowledgement without a second mutation. No production credentials, external GitHub mutations, or guard bypass were used in those tests.

Actual React setup components were also exercised in Chromium at desktop/mobile sizes and light/dark themes: 148 browser assertions passed, with 48 screenshots, no page errors and no external requests. The visual pass found and corrected prematurely cleared pending state, inconsistent migration progress text, an irrelevant option on the bootstrap action and an installed-runtime verification label that incorrectly implied a missing workflow. The compatibility unit suites passed 227 cases, and the adjacent ordinary Hosted/rotating recovery suite passed 166. These checks do not substitute for the separately tracked full Next dashboard and final live GitHub/OAuth gates.

Recovery's final adversarial implementation review found no remaining P1/P2 in the source-proof, replay, capability delivery or admitted recovery boundaries. Fresh exchange/prepare remains bounded by the original 15-minute manifest lifetime; already admitted claims retain only their existing native dispatch/recovery window.

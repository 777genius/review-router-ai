# ReviewRouter: единая настройка провайдеров, ключей и ревью

Дата: 26 октября 2026. Статус: план проверен тремя независимыми критиками GPT-6.1 Sol xhigh; после исправлений и повторной проверки все три дали GO. Это одобрение плана, а не подтверждение готовности ещё не выполненной реализации.

## 1. Решение

Доработать существующую систему настройки провайдеров. Основной поток: **провайдер → место хранения ключа → нужное подключение → модель → доступные настройки ревью → подходящая проверка**. Один и тот же провайдер не должен появляться в списке дважды из-за места хранения ключа.

Для OpenRouter, MiMo Token Plan и Kimi Code использовать уже существующие два radio-варианта, в указанном пользователем порядке:

1. **GitHub Secrets** — «Добавьте ключ в GitHub Secrets каждого репозитория».
2. **ReviewRouter** — «Ключ хранится зашифрованным и используется в подключённых репозиториях».

План сохраняет различия между провайдером, способом хранения credentials и исполнителем ревью. Эти различия влияют на доступные настройки, но пользователю не нужно разбираться в именах внутренних auth modes, sub2api или runtime profiles.

**Существенная часть запроса уже реализована в main через PR #708.** Необходимо проверить доставку этой версии, затем исправить оставшиеся дефекты формы, отображения возможностей, логотипов и проверок. Повторно строить хранилище ключей и систему установки не требуется. [S01, S02]

### Три существующих режима credentials

| Внутренний вид    | Фактическое поведение                                                                                                                                           | Представление пользователю                                                                    |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `gateway_binding` | Новый вариант ReviewRouter из #708: подключение к существующему Account Gateway, credentials остаются за этой границей; в CI передаются ограниченные полномочия | ReviewRouter, ключ зашифрован; выбор подключения только когда требуется                       |
| `user_ci_secret`  | Пользователь добавляет ключ в GitHub Secrets; сайт не получает его значение                                                                                     | GitHub Secrets; понятная инструкция для каждого репозитория                                   |
| `managed_api_key` | Ранее созданные OpenRouter/MiMo: ReviewRouter сохраняет ciphertext и при установке передаёт ключ в GitHub Secret; это совместимый старый путь                   | GitHub Secrets · managed by ReviewRouter, с коротким пояснением реального места использования |

Последний режим нельзя просто переименовать в новый ReviewRouter/Gateway. Это разные custody и исполнение. Существующие profile IDs, связи с репозиториями, ciphertext, rotation и default selections сохраняются. Смена способа хранения создаёт новое подключение и явно назначается нужным целям. Автоматического переноса ключей и массового перепривязывания нет. [S02, S11]

## 4. Целевой UX

### 4.1. Новый провайдер

1. Открытие нового Add provider без сохранённого выбора показывает поле **Provider** с placeholder. Профиль не выбирается по порядку массива.
2. После выбора OpenRouter, MiMo Token Plan или Kimi Code появляется общий **Key storage** с двумя radio. Сохраняются текущие defaults: Providers add — GitHub Secrets, Accounts key enrollment — ReviewRouter; валидный явный continuation intent имеет приоритет. Порядок radio всегда GitHub Secrets, затем ReviewRouter. Режим не переключается скрытно.
3. В GitHub Secrets не показывать Account и поле ввода самого ключа в ReviewRouter. Показать фиксированное имя секрета и существующий путь настройки после выбора целевого репозитория.
4. В ReviewRouter использовать существующую авторизованную Gateway-binding модель. Если нет доступного подключения, один понятный CTA **Connect account**, затем существующий Access/return flow с сохранением workspace и repository targets.
5. После готовности обязательных prerequisites показать выбор модели. Не требовать уже выбранной модели для отображения самого model picker.
6. После выбора модели и разрешения её возможностей показать только применимые настройки ревью, когда этот экран создаёт или изменяет workspace/repository selection.
7. Внизу — соответствующая проверка подключения или настройки GitHub и основное сохранение. Проверка не назначает provider и не сохраняет форму автоматически.

Сохранить текущий `modelOnly = adding && !makeDefault`: добавление переиспользуемого профиля без назначения default содержит модель и пояснение, где настраивается ревью. При Add + Use as workspace default появляются настройки создаваемой default selection. Само добавление профиля не создаёт несуществующую политику.

Выбор существующего профиля или workspace default сразу показывает сохранённую модель и настройки. Их нельзя скрывать только потому, что каталог временно недоступен: показываем сохранённое значение и состояние недоступности. Неизвестная capability при outage требует retry/объяснения; только подтверждённая несовместимость требует явного исправления saved value. Наследуемый default остаётся read-only там, где так работает существующая модель.

### 4.2. Когда нужен выбор аккаунта

Правило задаётся требованием **конкретного Gateway binding**, а не строкой названия провайдера или импортом sub2api в UI. Это соответствует пожеланию пользователя: account selector нужен только там, где выполнение действительно использует такое подключение.

| Состояние                                                                      | UI                                                                                                                                              |
| ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| GitHub Secrets                                                                 | Account отсутствует                                                                                                                             |
| Существующий managed API key                                                   | Account отсутствует; сохранённая connection identity не меняется                                                                                |
| Gateway: загрузка, неполная страница, denied или unavailable                   | Сначала соответствующее loading / Load more / retry / объяснение доступа. Ноль совпадений на неполной странице не означает отсутствие аккаунтов |
| Gateway: полная доступная выборка не содержит подходящих разрешённых аккаунтов | Один CTA подключения; не дублировать его пустым disabled-select и двумя одинаковыми инструкциями                                                |
| Gateway: ровно один подходящий аккаунт, и полнота списка подтверждена          | Компактное отображение выбранного подключения; можно не требовать лишнего клика                                                                 |
| Gateway: несколько подходящих аккаунтов или список ещё неполный                | Явный selector только подходящих провайдеру, протоколу, workspace и правам аккаунтов; сохранение пагинации                                      |
| Редактирование существующего Gateway-профиля                                   | Показать именно его binding, включая загрузку выбранной записи за пределами первой страницы                                                     |

«Один аккаунт» определяется после фильтрации и только при полном авторизованном inventory. Одна строка на первой странице не является доказательством единственного аккаунта. Автоматический выбор единственного аккаунта допустим только для нового нетронутого draft; refresh, отзыв доступа или появление новой страницы не заменяют сохранённый либо явно выбранный binding. Никогда не подставлять первый чужой или просто совпадающий по бренду аккаунт.

Если пользователь уже явно выбрал допустимый binding и он успешно разрешён, показывать Model можно сразу: загружать все остальные страницы ради этого не требуется.

Новый encrypted OpenRouter/MiMo/Kimi из #708 тоже идёт через Gateway; поэтому account selection для нескольких таких подключений корректен. Создавать отдельный прямой vault ради удаления dropdown не требуется.

### 4.3. Accounts и Providers

Общими остаются идентификация провайдера, storage radios, логотипы и copy. **Accounts** отвечает за credentials и доступ, **Providers** — за переиспользуемый профиль с моделью, а workspace/repository selection — за настройки конкретного ревью.

Не добавлять модель и параметры политики в credential enrollment только для визуального сходства форм. Подключение ключа не должно незаметно менять workspace default. Переходы Accounts → Providers и обратно используют текущий безопасный intent, очищают transient key и повторно проверяют права. Если enrollment завершён, а создание/назначение профиля не удалось, существующее подключение сохраняется как ещё не назначенное; повторяется незавершённый шаг без повторной загрузки ключа и дублирования аккаунта.

При изменении модели из Providers явно показывать, что она изменится для всех использующих профиль целей. В локальных настройках репозитория модель существующего профиля остаётся фиксированной; рядом допустима ссылка на существующее редактирование Providers. [S03, S12]

### 4.4. Геометрия формы и логотипы

- Model — полная ширина; длинные IDs корректно сокращаются/переносятся без горизонтального overflow.
- Поддерживаемые Review depth и Review engine — два одинаковых столбца на desktop, один на mobile; верх label и control совпадает. Если доступно только одно поле, лишней пустой колонки нет.
- Fast mode и Read related files — ниже, одной вертикальной группой. Ни одно поле не появляется только ради симметрии.
- Короткие hints относятся к своему полю; не создавать пустые тексты-заполнители ради высоты.
- Existing `SelectField`, `RadioCardGroup`, `Checkbox`, `Button` переиспользуются. Минимальный layout-fix в общем primitive делать только после проверки других его потребителей; локального `items-start` достаточно, если браузер подтвердит результат.
- Shared `ProviderLogo(providerId)` используется в выборе провайдера, аккаунтах, provider list, default/profile cards и строке текущего provider. Один размер рамки, одинаковый optical alignment в light/dark.
- OpenRouter/OpenAI/Claude и имеющийся Kimi SVG переиспользуются; MiMo получает проверенный локальный SVG из официального источника. Проверить происхождение/условия использования и безопасное содержимое. Не загружать логотипы с внешнего хоста на каждый render и не добавлять большую icon dependency ради одного знака.
- Бренд определяется безопасным ID из server view (`connection.provider`, существующая finite provider map), а не пользовательским label. Для отсутствующих метаданных — нейтральный значок, без предположения OpenAI.
- Логотип декоративный при видимой текстовой подписи; доступность не зависит от цвета или картинки.

### Важное ограничение direct OpenRouter reasoning

В текущем коде скрытый reasoning не означает отсутствие параметра: frontend создаёт `xhigh`, общий schema branch подставляет `xhigh` при omission, а runtime повторяет default. Поэтому простое удаление поля из JSX/JSON не исправляет wire behavior. Kimi имеет отдельный путь с отсутствием reasoning; переносить его на все бренды без анализа нельзя.

Для основного UX-изменения разделить уже поддерживаемый Read related files и остальные controls. Сохранить текущую семантику существующих OpenRouter selections. Этот batch также не меняет defaults при создании новых direct OpenRouter selections и schema/runtime fallback `xhigh`. Перед включением прямого OpenRouter Review depth проверить разрешённые значения конкретной модели и фактический outbound payload текущего runner в ограниченном fixture/spike. Spike не блокирует доставку остальных UX-исправлений; до положительного результата новые неподтверждённые reasoning controls не показываются. [S13, S18]

Новый режим «вообще не отправлять reasoning» для произвольных OpenRouter моделей — отдельная согласованная CP/runtime доработка. Если она потребуется, отсутствие старого поля нельзя переосмыслить как новый intent: нужен явный совместимый saved state, перенос через materialization/capture/checkout и runtime, проверка производителя, а также сохранение legacy semantics. Не добавлять такой режим автоматически как побочный эффект выравнивания формы.

Существующие подтверждённо неподдерживаемые сохранённые значения отображаются с просьбой явного исправления. Outage или неизвестные metadata не доказывают несовместимость и не вынуждают менять saved value. Render, refresh и открытие формы не переписывают сохранённый effort, в том числе legacy Codex Ultra и отсутствие account default из #710.

## 6. Проверка подключения без ложных обещаний

### ReviewRouter / Gateway

Переиспользовать `GatewayConnectionTest` и `createGatewayConnectionProbe`. Они уже работают по binding/model и не требуют отдельного ключевого сервиса для OpenRouter или MiMo. Условие отображения должно идти от пригодного Gateway connection target, а не бренда.

Probe делает один ограниченный запрос, перепроверяет live binding authority, ограничивает время/вывод и закрывает execution. Сохранить cancellation, запрет параллельного запуска, rate limit, безопасные сообщения ошибок и сброс результата при смене scope/binding/model. При полученном обновлении key/binding/access revision прежний результат также сбрасывается; если его актуальность неизвестна, это датированный результат прошлого запроса, а не утверждение текущего доступа. Использовать безопасные существующие metadata, не раскрывая браузеру Gateway authority. Existing probe не проверяет весь review engine, tool calling, качество ревью или каждый reasoning setting: UI говорит **«Модель ответила»**, а не «всё ревью гарантированно работает». [S08, S14]

Для каждого Gateway profile проверить допустимость сформированного probe payload через его qualified adapter. Например, текущий общий probe добавляет `service_tier: default` для non-Codex profiles, тогда как direct Kimi qualification исключает service-tier controls: это требует отдельной проверки конкретного Gateway route, а не переноса direct-результата. Controlled fixture обязан проверить фактические поля запроса, а не только вернуть success. Неподтверждённый profile не получает обещание поддерживаемого live test.

Для неготовой формы показывается один понятный prerequisite. Автоматически платные запросы при выборе модели или открытии диалога не запускаются.

### GitHub Secrets

Переиспользовать `CiSecretDelivery` и существующую workflow readiness. Текущий API GitHub позволяет получить имя и даты секрета, а не его значение. Проверка секрета и workflow — **Check GitHub setup**, с конкретным результатом: секрет найден / workflow настроен / требуется действие / нет прав проверки. [S15, E01]

Это не зелёный успешный Test connection. В отсутствие целевого репозитория объяснить, что настройка проверяется после назначения репозиторию. При ручном подтверждении не утверждать, что GitHub API подтвердил наличие.

Настоящий inference test GitHub-ключа потребовал бы ограниченного запуска внутри Actions с авторизацией, run/result correlation, защитой от повторов, лимитами и canonical runtime. Это отдельная возможность; она не входит в минимальное исправление данной формы. Нельзя извлекать секрет обратно или тайно сохранять вторую копию ради кнопки.

### Существующие managed API keys

Сохранить текущую установку, проверку GitHub setup и rotation. Не направлять такой профиль в Gateway probe без настоящего binding. В подробностях хранения дать уже существующий явный путь создания нового ReviewRouter-подключения, если пользователь хочет новый способ работы; назначение нового профиля — отдельное явное действие.

## 7. Архитектура и конкретные границы изменений

### Переиспользовать

- `apiKeyProviders`, `getApiKeyProvider`, `apiKeyProviderForGatewayProfile` — конечный список и существующие mappings.
- `ApiKeyStorageChoice` и `api-key-storage.ts` — одна разметка radio, одна copy и intent navigation.
- `ProviderModelFields`/`ProviderModelPicker` — единый renderer с независимыми признаками доступных полей.
- `useGatewayModelAccounts`, `useProviderModelCatalogs` — существующие каталоги, query keys, refresh и exact selected binding.
- `GatewayConnectionTest`, Gateway probe и credential delivery — существующие операции с их границами полномочий.
- Workspace provider registry и current selection settings — текущая persistence model.

### Минимальные новые части

1. Небольшой pure resolver готовности/возможностей формы в существующем provider-setup feature. Он принимает нормализованные текущие данные, возвращает видимость полей, разрешённые варианты и тип доступной проверки. Domain rules переиспользуются из review-providers; React не решает, что разрешено сервером.
2. Один renderer логотипа по upstream/provider ID и небольшое безопасное расширение read model там, где сейчас доступен только общий authMode. Не добавлять для этого таблицу или дублирующую provider registry.
3. Разделение существующего общего tuning gate на field-specific rules. Account capability data и direct descriptors остаются исходными источниками; не создавать ещё один независимый список допустимых моделей/efforts.

**DRY:** единый storage control/copy, renderer полей и логотипов, общие существующие каталоги. **SRP:** credentials, profile model, selection settings и диагностика сохраняют отдельную ответственность. **Dependency inversion:** UI получает безопасные feature data; он не импортирует sub2api SDK и не работает с ciphertext. **Clean Architecture:** authorization/save/runtime validation остаётся на серверных и доменных границах, UI capabilities не принимаются от браузера как доказательство.

Не нужны новый vault, SQL migration для storage, универсальный wizard engine, новый provider plugin framework, ещё один cache, замена Accounts целиком или перенос всего runtime в новый сервис. Изменение shared primitive ограничить подтверждённой проблемой layout. Если wire contract действительно меняется, это отдельный парный diff, а не скрытая часть frontend PR.

## 9. Проверка и критерии приёмки

Использовать существующие `scripts/accounts-reference-e2e`, Next.js, PostgreSQL и controlled Gateway/GitHub fixtures. Текущий `api-key-storage.spec.ts` уже покрывает три провайдера и оба пути. Старый `provider-model-catalog.spec.ts` использует прежние labels/маршрут; актуализировать его перед использованием как доказательства. Матрица ниже означает параметризованные critical contract/UI checks и несколько полных E2E по разным путям, а не полный cross-product всех провайдеров, ролей, ошибок и viewport.

| Область          | Обязательные сценарии                                                                                                                                                                                                                                                                                              |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Provider/storage | OpenRouter, MiMo, Kimi × два radio; ровно один вариант каждого в новом provider picker; переходы Accounts/Providers, single repo/bulk/workspace без потери target                                                                                                                                                  |
| Готовность формы | Пустое добавление; provider выбран; account 0/1/multiple/incomplete-page; ноль совпадений при дальнейших страницах; loading/denied/unavailable; модель ещё не выбрана; существующий профиль; workspace inheritance; modelOnly vs Add+makeDefault; refresh не заменяет выбранный binding                            |

Для настоящего backend/runtime поведения использовать реальные compiled components и controlled transport, а не mock собственной функции как доказательство E2E. Если меняется смысл captured reasoning, обязательна парная проверка с точными commits. Если меняется только UI, не запускать заново всю unrelated runtime qualification без конкретного риска или обязательного CI gate.

Проверки секретов разделены по наблюдаемым каналам. `noSecrets()` в browser E2E
проверяет URL, local/session storage, DOM и input после отправки/смены пути.
Дополнительный canary capture проверяет завершённые HTTP/SSR-ответы, browser console/errors,
новый `next-app.log`, маршрутный Gateway-log и JSON/HTML-снимки harness.
Проверять нужно журнал свежего процесса после изменения конфигурации; старый
журнал не переписывается для получения PASS. Next development logging аргументов
Server Functions выключается через `logging.serverFunctions: false`, поскольку
эти аргументы содержат transient API key/OAuth code; request/error logging
сохраняется.

React Query cache, mutation state, storage writes, продолжение после lost ACK и
безопасные ошибки отдельно проверяются существующим
[`account-gateway-account-controls.oauth.test.tsx`](../../apps/web/app/dashboard/account-gateway-account-controls.oauth.test.tsx)
через реальные экземпляры QueryClient и canary keys. Эти assertions не заменяются
проверкой только DOM. Снимки здесь означают сериализованные пользовательские
read models/SSR и диагностические JSON/HTML-артефакты приложения. Тестовая
Playwright trace намеренно записывает ввод синтетического canary и не является
продуктовым каналом хранения ключей; живые ключи в harness не используются.

Запрошенный live probe расходует квоту и доказывает один ответ выбранной модели в момент проверки. Controlled fixtures не являются live acceptance у провайдера. В итоговом отчёте отдельно указать проверенный код, смоделированные внешние системы и production delivery.

### Definition of done

- Новый пользователь выбирает бренд один раз, затем место хранения; нет технических дубликатов MiMo/OpenRouter/Kimi.
- Account виден только при реальной необходимости binding; нет списка несвязанных аккаунтов.
- До выбора провайдера нет преждевременного блока Model and review settings; после необходимых prerequisites модель и поддерживаемые controls появляются в правильном порядке.
- Рабочее чтение файлов доступно direct OpenRouter/Kimi; неподдерживаемые параметры не рекламируются.
- Test connection означает реальный bounded запрос; GitHub setup имеет отдельное честное название.
- Сохранённые профили и назначения не меняются из-за открытия формы, refresh или новой разметки.
- Поля выровнены, бренды правильны, mobile и keyboard flows проверены.
- Существенные замечания критиков и PR review устранены; CI и post-release проверка соответствуют точным опубликованным версиям.

## 10. Что специально не расширяется

- Не добавляется в этом UX batch отдельный inference workflow для GitHub Secrets.
- Не вводится незаметная миграция старых managed keys в Gateway.
- Не обещаются все Codex настройки любой модели OpenRouter.
- Не добавляются модель/политика ревью в обычную credential enrollment форму.
- Не расширяются Kimi Code до Moonshot API или MiMo Token Plan до любого endpoint с похожим названием.
- Не меняются memory, Skills, publication identity, release authority и другие независимые подсистемы.

Эти границы позволяют закончить понятный интерфейс и использовать существующую инфраструктуру, не превращая исправление экрана в переработку продукта.

Исследование и независимую критику выполнили три агента GPT-6.1 Sol с reasoning effort xhigh. Каждый прочитал полный первоначальный план; замечания были включены в текст, после чего каждый повторно проверил исправленные положения.

| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------- |
| Frontend / UX                       | Явный modelOnly при добавлении без default; приоритет loading/denied/incomplete над 0/1/many; отсутствие требования загрузить все страницы после явного выбора binding; честный источник model catalog; геометрия actual triggers | GO, блокеров нет        |

## Low-priority RFC 850 century boundary in RR

In ReviewRouter PR #1028 at `f2f3384c`, `packages/features/review-run-control/src/infrastructure/github/octokit-github-review-revision-source.ts` around lines 283–317 parses an obsolete RFC 850 two-digit year by choosing the current century and, if the resulting instant is over 50 years ahead, subtracting 100 years. At synthetic `now = 2099-12-31T23:59:59Z`, the `Retry-After` value `Friday, 01-Jan-00 00:00:02 GMT` can reasonably denote 2100-01-01, three seconds ahead. The parser constructs 2000 instead; the date in 2000 was Saturday, so the weekday round-trip rejects the input. On a 503, the rejected date becomes an absent Retry-After and the first jitter delay can be 0.5–1 second, permitting another read earlier than the intended three seconds if budget remains.

This is an artificial 2099/2100 boundary involving an obsolete date form, not an explanation for a 2026 incident. RFC 9110 specifies interpretation of dates appearing more than 50 years in the future as the most recent matching past year, but does not explicitly prescribe initial-century selection; choosing the nearest plausible 2100 value in this example should be reviewed against the intended interoperability contract. It is not valid to generalize the 503 outcome to every 403/429: rate-limit fallback and remaining/reset headers have separate behavior. Independent source inspection found the same current-century/subtract-only logic in public Action PR #411 at `4dcc3859`, `src/github/client.ts:385–409`; its generated runtime has not been rebuilt with those source changes. This finding was derived from source and calendar inspection, not an executed fake-clock test.

Suggested regression: fake clock at the exact boundary, 503 with this valid weekday/date and enough total read budget; assert that no next read starts before the intended three-second boundary. Add complementary cases at the 50-year pivot, December/January transitions, leap seconds, wrong weekday and invalid dates; preserve safe-method gating and total deadlines. Distinguish intentionally accepted interpretations from malformed values and avoid changing normal 2026 semantics without tests.

## Stream-stage diagnostics and custody limits

In deployed `6271ebe1`, the companion relay in `apps/api/src/review-run-gateway-relay.ts` tracks stages such as session, local authority/forward, SDK request and stream wrapping before headers, and upstream read, authority recheck, cancellation, native status, byte limits and downstream afterward. On EOF, status read, usage recording and dispatch settlement occur in sequence. Prior to PR #1028, usage and settlement failures could retain the misleading `native_status` phase. An upstream 502 or missing terminal frame alone does not identify the responsible component or prove that provider inference did not happen.

PR #1028 at `f2f3384c` adds separate `usage_outcome` and `companion_settlement` labels and narrowly allowlisted error properties; logger errors must not change settlement. Its six loopback stream tests inject stage and logger failures and check one POST, unknown custody, no terminal delivery and no secret strings. These are V1 in-memory binding/loopback fixtures: they are not a real PostgreSQL/native-provider E2E, proof of a historical root cause, or independently verified passing test results. `native_status` can also include an authority recheck, so the label alone does not prove a native status endpoint failed. On the separate responses-stream path, a failure after headers can result in a broken stream and unknown effect rather than a new HTTP 502.

Before release, run joined disposable PostgreSQL/Gateway/native fixtures with synthetic provider effects and fault injection after EOF for status, usage and settlement. Verify exact durable outcome, physical close acknowledgement, no replay and sanitized phase attribution under logger failure, concurrent lease loss and restart. Correlate historical incidents only with safe trace fields and actual owner/native evidence; do not log provider payloads, tokens or error messages.

The inspected current source creates normal `requestRef` values server-side from UUIDs, sometimes prefixed by a truncated reviewer hash; companion refs are server-created UUIDs stored in the durable row. This is not proof that every legacy row is safe or that a hash is anonymous. Test secret-like reviewer/dispatch inputs and any supported legacy-row behavior, with redacted test output, before broad claims about log privacy.

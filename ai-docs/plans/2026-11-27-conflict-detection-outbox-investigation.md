# Conflict-review detection failures and dispatch concurrency

Read-only production investigation around 14:49–14:52 UTC on 27 November 2026, independently checked against deployed ReviewRouter source `6271ebe1`. This is a separate issue from the relay/model-request fixes in this PR. The production root cause of the dead letters, actual duplicate dispatches and customer impact are **not established**. No event was replayed and no production state was modified.

## Production evidence and scope

Among outbox events created in the preceding 24 hours, 1,947 had current status `processed` and 129 had status `dead_letter` for type `conflict_review.detection_requested`; creation time is not the processing time. The dead-lettered events ran out of their 5/5 attempts with `handler_error` and sanitized summary `outbox_handler_failure`; their separately inspected dead-letter timestamps were 26 November 22:12 through 27 November 13:27 UTC. An independent aggregate check confirmed the count and timestamps.

For events created after the current deployment cutoff (04:57:09 UTC), 21 events both originated and reached dead letter in the current version, across three repositories in one GitHub installation; 9 were base-push and 12 pull-request events. In the same created-after-cutover cohort 738 events of this type were `processed`. These are event counts, not 21 failed ordinary AI reviews or 738 successfully launched conflict reviews. `processed` also covers skipped, disabled, ineligible and no-conflict outcomes. Conflict-head fallback eligibility requires specific merge-conflict, repository and rollout conditions; determine actual per-PR effects only through authorized, bounded investigation.

`handler_error` is the generic mapping for an unhandled or unrecognized exception. The outbox safe summary deliberately hides the underlying exception. It therefore does **not** establish whether GitHub, Prisma, workflow capability, a rate limit or another phase caused these specific failures. A bounded worker-log slice around 13:20–13:31 did not expose the underlying exception for the three events near 13:27; log retention and redaction limit conclusions. Do not print raw payloads, credentials, nonces, review contents or unbounded error messages to improve attribution.

Other global outbox figures were approximately 7,980 `pending` and 4,641 `dead_letter` across historical event types at 14:50 UTC. Those totals are not a count of currently broken queue jobs. In particular `review.run.authorized` is not registered as a known handler in the inspected worker and null claims/next-attempt fields alone do not prove a stuck worker. Investigate each event's consumer and retention contract separately.

## Source-level races requiring isolated reproduction

The current flow is webhook pull-request/base-push → `request-conflict-review-detection.ts` → `conflict-review-detection-requested-handler.ts` → `process-conflict-review-detection.ts` → repository/rollout and GitHub capability reads → eligible conflict-head attempts and `repository_dispatch`. A base-push event may process multiple PRs, so a later handler exception does not establish that earlier external effects did not happen.

1. **Accepted POST with ambiguous or failed settlement.** In `process-conflict-review-detection.ts:282–316`, the GitHub dispatch and `markAttemptDispatched` are in the same `try`; an exception invokes `markAttemptFailed`. If GitHub accepts a POST but its response is lost, or a later database mark throws, retry can refresh the failed/recorded attempt with a new random dispatch ID and nonce and POST again. This follows from the inspected control flow, not from a reproduced production duplicate. Do not mass-requeue these dead letters until external acceptance and idempotency are resolved.
2. **Identity race during exchange.** In `prisma-conflict-review-repository.ts:241–260` the exchange reads and checks the current dispatch ID and nonce. Its later `updateMany` at 299–320 checks attempt ID, status and run/config conditions, but does not include that dispatch ID or nonce in the update predicate. Independently inspected source shows a concurrent `refreshAttemptDispatch` at 134–163 can replace ID/nonce while keeping `recorded` and clearing run/config, between the read and update. A stale exchange can then update the refreshed row and return the old ID. Expected downstream rejection or later lookup failure is not proof that external publication cannot happen; test exact outcomes rather than assuming one.
3. **Late mark versus refresh.** Refresh is allowed for `recorded` or `failed` attempts, including a concurrent duplicate detection before an earlier POST returns. `markAttemptDispatched` at 116–131 predicates on attempt ID and `recorded` status, not dispatch identity; `markAttemptFailed` at 189–205 predicates on attempt ID and active statuses. A late mark belonging to the old identity can therefore affect the refreshed identity. Adding identity conditions is necessary to evaluate but alone does not settle unknown GitHub POST acceptance or prove exactly-once external execution.
4. **Same-run attempt ordering.** The exchange checks stale `githubRunAttempt` before its update, but that check is not restated in the update predicate. Two exchanges for the same GitHub run with different attempt numbers may interleave; verify with PostgreSQL barriers whether a stale attempt can overwrite the newer one. Existing `conflict-review.test.ts` cases use sequential in-memory or stub Prisma scenarios; they do not demonstrate these real SQL interleavings.

Existing safeguards matter: the exchange receives OIDC claims verified by the calling boundary, checks repository and run claims, dispatch ID/nonce, revision, active status and TTL, and binds one GitHub run ID to an attempt. The repository method itself does not establish the cryptographic verification. A previous job exchanging only after identity refresh should fail verification; an earlier job that already exchanged is a different case. Passing a dispatch ID/nonce through `reviewrouter-conflict-reusable.yml` is not by itself proof of one physical execution across refreshed identities. The code observations above do not demonstrate actual duplicate inference, billing or incorrect publication in production.

## Safe next steps and acceptance

- Add bounded diagnostic phase/error classification and correlation using server-generated opaque values; separate pre-dispatch read failure, POST outcome unknown, and post-POST database settlement failure. Preserve existing secret/body redaction and use no raw provider text.
- Reproduce each interleaving with real disposable PostgreSQL barriers: old exchange read → refresh → old update; refresh concurrent with late success and failure marks; competing run-attempt numbers; accepted POST with dropped response; accepted POST then database error; and duplicate/base-push multi-PR processing. Assert row identity, status, current run and publication authorization on both orderings.
- Design a durable, bounded recovery protocol for unknown external POST effects and identity-scoped CAS. Explicitly handle old/new executions and compensation; do not assume a failed local mark proves GitHub rejected the request. Keep unrelated PRs concurrent and avoid new credentials in CI.
- For the 21 current-version dead letters, obtain only authorized correlation-safe evidence to identify failure phase and affected functionality. Reconcile GitHub and durable attempt state before considering any individual replay; never blindly requeue a batch. Prove the final change through a disposable App-first E2E, independent review, migration/rollback planning if needed and the repository deployment registry.

Infrastructure context at the same bounded inspection: PostgreSQL and Gateway active, migration table had no unfinished migrations, site and API certificates expire in January 2027, pgBackRest reported the latest scheduled backup successful. This is health evidence, not a restore test or proof that all other production requests succeed.

# Webhook effect fence (work in progress)

- Scope: future additive database schema and guarded webhook effects.
- Staging: `pending`; the protocol is not integrated or qualified.
- Production: `pending`; do not install or enable takeover.

The design, database-effect fence primitives and prototype adapters (app-authorization revocation, pull-request pre-admission and repository metadata) are incomplete. The fenced adapters are not selected by HTTP routes and must not be used to reclaim a live or legacy delivery until every effect writer, external effect and mixed-version transition meets the [fencing contract](../architecture/2026-11-27-webhook-delivery-fencing.md). A lease alone is not proof that the earlier worker stopped. This draft does not implement GitHub redelivery or recovery of old `processing` rows.

Worker qualification so far: isolated PostgreSQL 17 and the generated Prisma 7.9 client built from the draft schema exercised claim/renewal, stale fencing, concurrent takeover, rollback after expiry, and the app-authorization adapter's atomic revocation, completion-failure rollback and stale-owner rejection. A separate mock-based pull-request ingress test exercises transaction binding and identity rejection; it is not a real-PostgreSQL integration test. The combined fixture passed 13 tests; no current route was changed or production data replayed.

The experimental repository adapter takes the global scope/epoch before its delivery fence and retains the existing repository authority guard. Its four isolated PostgreSQL/Prisma tests cover normal mutation, completion rollback, stale-owner rejection and one three-party authority-change/takeover race. The earlier 28 mocked repository regressions also passed. These fixtures do not establish complete scope-writer participation, correct mixed-version rollout, production safety or general deadlock/throughput behavior.

The experimental setup pull-request adapter now runs the existing provisioning transition inside the guarded transaction but deliberately leaves the composite delivery in `processing`. An isolated fixture passed seven existing and one prototype mock tests plus three PostgreSQL/Prisma tests (success, stale owner, rollback when the lease expires during a delayed DB write). The worker fixture supplied protocol/domain shims; full project CI and composite end-to-end behavior remain pending.

The experimental installation adapter reuses the existing installation, owner grant and sync-outbox logic inside one fenced transaction. Three mock-based adapter tests and eight existing mock/in-memory tests passed on the worker. Three additional isolated PostgreSQL/Prisma tests cover commit, rollback on terminal failure, and stale generation rejection. These tests do not establish concurrent takeover races; production routes do not select the adapter. Failure recording after rollback, composite handler integration, scope-writer participation and mixed-version behavior remain unresolved.

A separate prototype composes pull-request ingress and setup DB effects under a single scope/delivery transaction including its terminal transition. It includes the optional conflict fallback via the existing outbox writer and fails closed if its existing rollout-policy decision is absent. Three mock composite tests and 11 existing adapter tests passed on the worker; seven isolated PostgreSQL/Prisma tests cover composite commit, policy allow/deny, outbox rollback when setup, conflict insertion or terminal transition fails, and one scope-change/takeover race. Route selection and a full mixed-version protocol remain unimplemented.

The experimental push adapter writes its conflict fallback request and terminal transition in the same fenced transaction, with a caller-supplied existing rollout-policy decision. Four isolated PostgreSQL/Prisma tests cover commit, rollback, deny policy, stale owner and payload mismatch. It is not routed; concurrent takeover, handling of invalid outcomes, full writer participation and mixed-version deployment remain unproven.

The WIP fence additionally stores an App identity hash and compares it for renewal, reclaim and guarded effects; an isolated PostgreSQL test rejects a different App hash and a duplicate cross-App GUID. A draft verifier derives the hash from trusted App configuration after HMAC verification, and a synthetic Fastify+PostgreSQL test binds the verified body to a fence. The live route is not wired, and trusted configuration must establish that the secret belongs to the configured App. The migration is draft-only, routes are unchanged, and no takeover is authorized.

A separate draft recovery custody table and DB-only operations reserve at most one redelivery request with an attempt owner hash, retain unknown outcomes, allow only that owner to record 202 as accepted rather than complete, and require exact receiver terminal evidence. Five isolated PostgreSQL tests cover reservation races, identity conflicts, unknown outcomes and the synthetic HTTP-to-fence path. A draft App-JWT client and bounded polling implementation exist but are not wired or invoked against GitHub. The synthetic fake-server/PostgreSQL fixture exercises one POST, lost-response suppression and receiver-side confirmation. The current authority only permits already-ingressed fenced failures with a known payload hash; deliveries never received by ingress remain unsupported. Automatic replay and production recovery are not implemented.

Before any rollout, finish the handler and outbox integration, durable claim/renewal and unknown-outcome protocol, and execute the isolated real-PostgreSQL and end-to-end race matrix in the design. Review the final schema, database privileges, indexes, migration version and mixed-fleet rollback independently. Apply migrations and rollout only after the exact integrated change is approved; preserve legacy rows and unknown effects. Record actual versions and evidence per environment here.
